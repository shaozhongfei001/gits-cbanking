# W5｜PLAN（三条硬约束的机械防线）

> 本 Wave 的存在理由：**约束①「不能同时手工维护两份可独立修改的定义」目前**只写在文档里，
> 没有被机械保障。若 V4 检不出越权写，按论证件 §4.1(3) 应**收窄并行范围**而非改用 A/B。

## 目标

把上游判据 V3 / V4 变成**可执行、可变异自证**的门禁。

| WP | 门禁 | 判据 | 独占文件 |
|---|---|---|---|
| **WP5.1** | **引用锚定**：地图引用本体/注册表中不存在的个体 ⇒ **拒绝** | **V3** | `scripts/gk17_ref_anchor_check.py` |
| **WP5.2** | **三处一致性**：地图 / 本体 / 投影 不一致 ⇒ **检出** | **V4** | `scripts/gk17_triple_consistency_check.py` |
| **WP5.3** | 本 Loop 全部新增门禁的**变异回归** | 每门禁自证 | `scripts/gk17_mutation_regression.py` |

## 实测缺口（W0/W1 侦察所得，非推测）

- **`KM-` 无独立 registry**，既有 `scripts/validate_knowledge_architecture.py` **不核对地图间引用**；
- **`KD-` 无前缀契约、无注册、无校验**；
- **`SIM-CAP-` 在 GK-KE 侧无前缀契约**；
- ⇒ 上述三处正是 WP5.1 的靶子；且必须**复用**既有校验器的定义，**不得另造一套**
  （否则本身违反约束①）。

## ACCEPT 判据（**每门禁各自自证**）

> **变异前 PASS / 变异后 FAIL / 恢复 PASS**

三者缺一不可。只做"变异后 FAIL"而不做"恢复 PASS"，无法区分
「门禁真的检出了变异」与「门禁本来就红」。

## 强制附加要求

1. **必须附变异负例**（本仓硬约束 #2/#3）：不做负例的门禁视为**未完成**；
2. 声称"全绿"前必须问：**它会不会因为夹具缺失而空转？**
   （本仓已有 6 个 Loop 首报全绿实为空转的前例）
3. 变异必须用**临时副本**，原文件逐字节复原并自证 —— 不得为了测试而改动权威源。

## 并发纪律

WP5.1 / WP5.2 由**两个独立写者并行**（文件互不重叠）。
两者**均不得**运行 `make generate` / `make check` / `run_gates.py` / `mvn` ——
门禁执行由 TL **串行**完成（依据 GK16 T-24 实测：并发会互相污染证据产生假 FAIL）。
