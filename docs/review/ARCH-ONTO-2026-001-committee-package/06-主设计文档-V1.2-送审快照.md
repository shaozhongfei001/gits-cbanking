## 1. 执行摘要

当前 GITS-KERT 体系的本体模型处于**「一份 OWL 合同、五处平行定义、四套命名体系、决策四度反转」**的混乱状态（§2 逐项举证）。本设计提出**三层归属模型**：

1. **GITS 放什么**：收敛为 `gits-operational.owl.ttl` 运营控制面本体，**留下 19 类 + 19 属性**（§4）；**迁出 13 类 + 16 属性**（§4.3）。
2. **KERT 放什么**：新建 `kert-product-knowledge.owl.ttl` 产品与知识供给域本体，**迁入 2 类 + 6 属性、新增 7 类 + 6 属性**（§5）。
3. **公共模块放什么**：在 KERT 仓根新建**可独立剥离**的 `public-ontology/` 模块（`public-kno.owl.ttl`），**11 类 + 9 属性 + 1 数据属性**，契约号 `CTR-SEM-003`（§6）。
4. **国标如何继承**：GB/T 48000.3-2026 为「标准数字化」领域标准，本项目采取**参照适用**——继承其建模通用要求并固化为 9 条可执行规则 R1~R9 + `make conformance` 符合性门禁；不继承标准数字化专有实体（§7~§8）。
5. **现在如何改造**：Wave 0~5 六波改造，约 7.5 人日，每波有明确验收判据（§10）。

**核算自洽性**：GITS 19 + 公共 11 + KERT 2 = **32 类** ✓；GITS 19 + 公共 9 + KERT 6 = **34 对象属性** ✓（+1 数据属性随 Customer 入公共模块）——与实测基线逐项对齐，无增无减。

**V1.2 相对 V1.1 的变更**（合并评审简报补缺）：① 修正拆分操作的生成物纪律（SHACL 为 `generated/` 生成物，拆分必须走「改源 → 登记 → `make generate`」链路）；② 新增 R9（`owl:imports` 钉 `versionIRI`）及 SHACL↔本体一致性、变更影响面分析两项门禁；③ 新增「公共模块被 KERT 事实私有化」与「产品关系零实例」两项风险；④ 新增 §2.0 事实基线与 §12 九问预审回答、附录 C 不确定项声明。

### 2.3 混乱的根因（架构归因）

1. **无归属判据**：32 类混在一起，从未回答「这个词该谁管」——类定义、实例权威、消费方三者错位。
2. **无公共层**：跨仓共享词汇没有中立归属地，只能寄居某一侧，造成权威循环（§2.0）。
3. **无可执行建模规范**：没有命名空间白名单、版本/扩展纪律、符合性门禁，命名空间错配可「静默绿」通过 CI。

## 3. 设计原则与三条划分判据

### 3.1 设计原则

- **P1 单一权威（SSOT）**：每个类有且仅有一个定义权威；每个实例有且仅有一个实例权威。类权威与实例权威**允许分离**，但必须在类元数据中显式声明。
- **P2 归属先于实现**：先判定每个术语的归属层，再动文件；判定规则本身先于判定结果冻结。
- **P3 跨仓零直读**：GITS 与 KERT 运行期**不跨仓读文件**；跨层引用一律「本地副本 + 内容哈希钉值 + 带外核验 + 漂移具名拒绝」。
- **P4 契约先行**：任何本体变更先改契约登记（`CTR-SEM-002`/`CTR-SEM-003`），再改源制品，再 `make generate` 产出生成物，最后改消费侧。**禁止手改 `generated/`**。
- **P5 fail-closed**：未知字段拒绝、歧义拒绝、默认拒绝；校验「空转」（vacuous）视为**失败而非通过**。

### 3.2 三条划分判据（判定规则，先于判定结果冻结）

| 判据 | 含义 | 典型例 |
|---|---|---|
| **A 跨域共享** | 类被 GITS 与 KERT **两侧**引用 | `Customer`、`Product`、`KnowledgeMap` |
| **B 域引用类** | **类定义**在公共模块，**实例权威**在他处 | `Customer`（实例权威 EDWCRM）、`Product`（实例权威 KERT 产品卡） |
| **C SSOT 在 KERT 工作区** | 供给/路由词汇，其权威源在 KERT workspace | `KnowledgeMap`（地图 SSOT）、`ActivationContract`、`Asset`、`Skill` |

**判定算法**：满足 A 或 B 或 C ⇒ 公共模块；仅为 GITS 运营控制面服务 ⇒ GITS；仅为 KERT 产品与知识供给域服务 ⇒ KERT。判据冲突时优先级 **B > C > A**（实例权威声明优先于消费面）。

**覆盖性验证**：32 类经附录 A 逐项判定，穷尽（无遗漏）且互斥（无双归属）；不存在「两边都不认」或「两边都要」的类（评审简报 Q1 闭环）。

- **`Task` 留 GITS、`TaskType` 入公共的自洽性**（评审简报 Q2 的闭环论证）：二者是**实例/词表**关系而非同类概念——`Task` 是**运营运行时对象**（有状态机、有办理人、实据 `human-action.Task` 与 V012 `task` 表，仅 GITS 读写），`TaskType` 是**受控词表项**（枚举空间，被地图/激活合同的 `entrypoint` 取值引用，判据 A+C）。类比：`Claim` 留 GITS 而 `ClaimType` 作为枚举值域存在。词表上收公共、实例留在域侧，符合 P1「类权威与实例权威允许分离」。
- `Action`/`Receipt` 与 Java 侧 `ControlledAction`/`ActionReceipt` 的命名差异为**既有去重裁定**，本次**维持**，不改名。

### 6.4 防私有化治理条款（回应「寄放 KERT ⇒ 事实私有化」风险）

11 类中 6 类（`TaskType`/`KnowledgeMap`/`Asset`/`Skill`/`ActivationContract`/`Capability`）实例 SSOT 全在 KERT workspace，存在「公共模块沦为 KERT 私有扩展」的结构性风险。治理条款：

1. **独立 Owner 与变更共审**：公共模块的任何变更须 GITS 侧与 KERT 侧**双侧 Owner 共签**（单侧提交不得合并）；`CODEOWNERS` 显式登记。
2. **命名空间与 ID 空间白名单**：`namespaces.json` 冻结可用前缀与 ID 空间；KERT 私有 ID 模式（如 `KS-*`、`HG-*`、`SQ-*`）**禁止**写入公共模块（它们属 KERT 域实例，不进 T-Box）。
3. **生命周期独立**：公共模块独立 `VERSION`/`CHANGELOG`/发布节奏，不随 KERT release 列车。
4. **GITS 侧对等消费权**：GITS 对公共模块的引用（`owl:imports` 副本 + 钉值）与 KERT 完全对等，任何「仅 KERT 消费」的类不得进入公共模块（判据 A 强制）。
5. **命名空间中立项联动**：若 §11 裁定中立前缀，私有化风险进一步结构性下降。

### 6.5 剥离预案

- 命令备查：`git subtree split -P public-ontology -b public-ontology-export`，产物经哈希校验后推送独立仓。
- 剥离触发条件（任一）：① 第三方系统接入需要独立发布本体；② 公共模块 Owner 与 KERT Owner 分离；③ 监管/行内要求本体资产独立纳管。
- 剥离后 GITS/KERT 消费方式不变（仍为「本地副本 + 钉值」），仅钉值源仓库地址变更。

### 6.6 命名空间（待裁定，见 §11）

方案一：沿用 `https://gientech.com/gits/kno/`（零 IRI 改动，重钉成本最低）。
方案二：中立前缀（如示意 `https://ontology.bank.example/kno/`，独立性最强，但需全量改 IRI + 双侧重钉，须企业域名裁定）。

### 7.2 适用边界声明（必须先声明，避免过度声称合规）

GB/T 48000.3-2026 面向**标准数字化**领域的**标准本体**（核心实体为 `Standard`、标准要素、层次结构、信息单元、制定程序等）。本项目是**企业运营域本体**，因此采取**参照适用**：

- **不继承**：「标准实体/要素/层次/制定程序」等标准数字化专有实体。

> 关于「不继承是否构成规避」的预审回答（评审简报 Q6）：**不构成**。参照适用（apply by reference）是国标对企业域应用的常规适用方式；本设计对通用要求**全量继承并加严**（如 vacuous=失败严于一般通过判定），仅排除与本领域无关的专有实体，且在 `ONTOLOGY-CONFORMANCE.md` 中逐条声明继承/不继承及理由，属**明示裁剪**而非规避。
>
> 该边界将**显式写入** `public-ontology/ONTOLOGY-CONFORMANCE.md`；**条款级引用以标准正式文本为准**（本稿依据官方平台元数据与公开摘要，正式文本获取后须复核 R1~R9 映射并更新符合性声明——列为 §10 前置动作，见附录 C）。

## 附录 C：不确定项与声明

1. **国标条款细节**：R1~R9 所列「IRI 唯一 / 序列化 / SHACL / 版本替代」等方向基于官方平台元数据与公开摘要的转述，**待 GB/T 48000.3-2026 原文核对**后方可升级为条款级引用；标准编号与发布/实施日期已官方核实。
2. **`gits:Product` 的注释**为 GITS 本体原文，代表**声明层面的自我定位**；其与 KERT 产品卡的实例级一致性**未做代码级验证**（且受 R-6 零实例现状限制，当前不可验证）。
3. **KERT 侧新增类名**（`KnowledgeItem`/`Segment`/`ProductInterpretation`/`RuleBundle`/`Projection` 等）为**建议命名**，实据已在 KERT 代码中定位，但命名需与 KERT 既有 ID 空间约定复核后方可冻结。
4. **`modules/operational-ontology` 规模两口径并存**：核心包口径 28 record + 14 enum + 55 Port；评审简报口径约 104 record/enum + 53 仓储接口。两口径统计范围不同，待 Wave 0 建表时统一核实（不影响 32 类 OWL 基线）。
5. **工时为量级估算**：Wave 0~5 共约 7.5 人日为架构量级估计，非工期承诺；「该迁移」判定基于权威源归属，未包含工作量承诺。
