## E1 权威循环：「产品」类在 GITS，却自述数据权威在 KERT；KERT 又钉 GITS

**证据 1a**——GITS 词汇表中「产品」类的定义原文（`gits-core.owl.ttl` 第 127-129 行）：

> `gits:Product a owl:Class ;`
> `  rdfs:label "Product"@en ;`
> `  rdfs:comment "产品身份（域引用类）。**权威物理源为 KERT 产品卡 product_id（03_core/\*/product-cards/PROD-\*.md）；GITS 侧无产品运营类。**"@en .`

**证据 1b**——KERT 侧的副本登记原文（KERT 仓 `90_control/ontology/PROVENANCE.json`，摘字段）：

> `"contractId": "CTR-SEM-002",`
> `"authorityRepo": "gits-cbanking",`
> `"version": "CTR-SEM-002@sha256:705578d6324abd0c",`
> `"pinnedAt": "2026-09-16"`

**解读**：「产品」这个概念的**定义**放在 GITS（1b 证明 KERT 钉的是 GITS 的表），定义里却写明**数据权威在 KERT**（1a）。两套仓库互为权威，任何产品词汇变更都不存在单一决策方。

## E2 校验假绿：前缀不一致，校验器一条数据都没校验到却显示通过

**证据 2a**——产品实例文件第 1 行原文（`products.ttl:1`）：

> `@prefix gits: <https://gits.bank.example/ontology/core#> .`

**证据 2b**——词汇表使用的命名前缀（`gits-core.linkml.yaml:7`）：

> `"gits": "https://gientech.com/gits/kno/"`

**证据 2c**——缺陷登记记录（GK17 Loop `FAILURES.md`，条目 `NAMESPACE_MISMATCH_SILENTLY_GREEN`）：实例校验 `targetedInstances=0`、`vacuous=true`（匹配 0 条实例、校验空转、状态显示通过），当前状态「待裁定」。

**解读**：两个前缀字面不同 ⇒ 校验器在 4,714 字节的产品数据里**未匹配到任何一条实例** ⇒ 「0 条数据 0 条违规 = 通过」。质量门禁在静默失效。本方案的 R4 规则规定：空转一律视为失败，除非显式豁免登记。

## E3 权威错位：GITS 数据库表自述「我不是产品卡权威源」

**证据**——GK17 Loop 工作记录 `W3-PLAN.md` 第 15-16 行原文：

> 「仓内无产品卡副本（`PROD-*.md` 零命中、无 `03_core/`）⇒ 产品卡的**权威源在工作区外**。
> V021 头部自己也写明：『本表为产品知识版本元数据，**非产品卡权威源**；产品卡权威源在 KERT workspace』。」

**解读**：GITS 数据库里的产品知识表自己声明不是权威源，但「产品知识卡」「产品知识版本」两个概念的**类定义**却放在 GITS 词汇表里——类放错了地方，应迁往权威源所在的 KERT。

## E4 同一概念多处定义，互不同步

**GITS 侧：本体概念至少 5 处平行定义**——① Java 领域类（28 个）；② 设计时语义合同（32 类 OWL/LinkML）；③ 场景种子文件 `ontology_seed.json`（32 个对象类型，其中含 Party/Utterance/Need 等**在两份正式定义中都不存在**的类型）；④ 设计文档与中英对照表；⑤ 数据库建表脚本（V001~V013）。

**KERT 侧：4 层定义互不同步**——① OWL/SHACL 副本层（即 E2 中校验空转的那层）；② 控制面 JSON 层（7 张知识地图、路由策略、激活合同；其中激活合同引用的若干资产/技能 ID **在 KERT 仓内没有定义文件**）；③ 代码硬编码层（技能路由代码中写死 7 个地图 ID，绕过控制面）；④ 技能包/文档层。

**结构性重复**（GITS 侧）：能力（Capability）登记在三个文件中数量互不一致（12 个 / 6 个 / 11 个）；知识地图与激活合同存在两套平行 Schema 家族（KM-\* 系与 SIM-\* 系）。

## E5 命名混乱：同一批技能三套命名互不重合

| 命名体系 | 示例 | 出现位置 |
|---|---|---|
| `bank-front-*` | bank-front-supply-chain-graph | 技能包目录 |
| `skill-customer-*` | skill-customer-previsit-report | 代码注册表、地图引用 |
| `SP-*` | SP-15、SP-20、SP-21 | 代码注册表、仓根技能目录 |

**解读**：三套命名互不重合，导致代码中的标识符校验规则被迫放宽以同时容纳两套写法；知识条目编号不连续且混入旧编号。命名归一已列入后续工作（不在本次范围），但它说明「无建模规范」的代价。

## E6 决策四度反转：同一问题反复重决策

| 时间 | 决策 | 内容 | 结局 |
|---|---|---|---|
| 早前 | D3-A | KERT 不内置本体 | 被推翻 |
| 2026-09-16 | D-31 | KERT 内置副本 + 哈希漂移检测 | 现行机制 |
| 其后 | ADR-018 | 「三层治理 + 公共本体临时寄放 KERT」 | **已作废（SUPERSEDED）** |
| 2026-09-20 | 拆分设计 V1.0 → 送审 V1.2 | 三分拆 + 公共模块 + 国标继承 | **本次送审** |

**解读**：每次反转的根因相同——缺少「归属判据」与「公共层」，方案只能在两个仓库之间摇摆。本次送审方案先把判据（A/B/C 三条）冻结，再按判据逐个判定 32 个概念的归属，判据不变则结论可复核、可重算。
