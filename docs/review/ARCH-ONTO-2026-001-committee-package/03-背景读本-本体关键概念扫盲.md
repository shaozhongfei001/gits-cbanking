# 背景读本二：本体关键概念扫盲（约 10 分钟）

> 本读本用项目实例解释评审所需的全部概念，不预设任何本体或语义网知识。

## 1. 本体是什么

**本体 = 一份机器可读的业务词汇表**，包括：概念（类）、概念的属性、概念之间的关系、以及约束规则。机器靠它在运行时理解「这条数据是什么、合不合规」。

本项目的本体用 W3C 国际标准技术书写：**OWL**（定义类与关系）、**Turtle**（文本格式，人类可读）、**SHACL**（定义校验规则，如"客户必须有客户号"）。

## 2. 类与实例；类权威与实例权威（本方案最关键的一组概念）

- **类**：概念的定义。例如「客户：有客户号、名称、证件号……」。
- **实例**：具体数据。例如「客户号为 C001 的某某公司」。
- **类权威**：这个概念的**定义**放在哪、由谁维护。
- **实例权威**：这个概念的**数据**以哪个系统为准。

关键洞察：**类权威和实例权威可以、也经常分离**。例：

| 概念 | 类定义适合放哪 | 实例数据权威在哪 |
|---|---|---|
| 客户 | 中立的公共模块（两套系统都要用） | 行内 EDWCRM 系统（既不是 GITS 也不是 KERT） |
| 产品 | 中立的公共模块 | KERT 的产品知识卡 |
| 知识地图 | 中立的公共模块 | KERT 工作区 |

本方案的判据 B 就是处理这种分离：**类定义上收公共模块，实例权威原地不动并在类元数据中显式声明**。

## 3. 版本「钉值」

两套系统不互相读文件，那 KERT 怎么保证用的词汇表和 GITS 一致？做法是：KERT 保存一份副本，并记录该副本的**内容哈希**（类似指纹），格式如 `CTR-SEM-002@sha256:705578d6…`。每次使用前校验指纹，不一致就具名报错拒绝运行。这与软件工程锁定依赖版本同理，称为「钉值」。

## 4. 权威循环（缺陷一，本项目真实存在）

```
GITS 词汇表中的「产品」类注释写着：
   「权威物理源为 KERT 产品卡」          ← 类在 GITS，却说数据权威在 KERT
同时 KERT 的副本登记写着：
   「authorityRepo: gits-cbanking」      ← KERT 又把 GITS 的词汇表当权威钉住
```
类权威在 GITS、实例权威在 KERT、KERT 又钉 GITS——**两仓互为权威，变更时无人有权单独拍板**。解法：类定义上收到中立的公共模块，两侧都只钉公共模块、各自声明实例权威，循环消解。（原文摘录见证据 E1）

## 5. 校验「假绿」（缺陷二，本项目真实存在）

SHACL 校验器按命名前缀匹配要校验的数据。本项目产品实例文件使用前缀 `https://gits.bank.example/ontology/core#`，而词汇表使用 `https://gientech.com/gits/kno/`——**两个前缀不同，校验器一条实例都没匹配到，匹配数 = 0**。但「0 条数据、0 条违规」在报告里显示为**通过**。这就是「假绿」（技术术语 vacuous）：校验空转却显示成功。本方案规定：**空转一律视为失败**，除非在符合性报告中显式登记豁免（写明原因、责任人、解除条件）。（原文摘录见证据 E2）

## 6. 「参照适用」国标

GB/T 48000.3-2026 是为「标准数字化」领域写的本体建模标准（它要建模的对象是"标准文件"本身）。本项目建模对象是银行运营概念，领域不同，因此采用**参照适用**：继承其通用建模要求（命名唯一、形式化、约束验证、版本管理、元数据等），**明示裁剪**其专有实体（标准文件、章节层次、制定程序等与本项目无关的概念）。这是国标在企业域应用的常规做法；方案对通用要求不仅全量继承，还加严（如「假绿」按失败处理，严于一般惯例）。

## 7. 一分钟词汇表

| 词 | 含义 |
|---|---|
| 知识地图 | 一份「做什么任务需要哪些知识」的装配清单 |
| 激活合同 | 执行某类任务前必须满足的条件与资源的契约 |
| 技能（Skill） | 可被调用的一个知识加工能力（如"生成访前报告"） |
| 产品知识卡 | KERT 维护的一份产品说明（定义、卖点、准入、风险提示） |
| 主张 / 证据 | AI 或人提出的待核实说法 / 支持该说法的可定位来源 |
| 人工门禁 | 必须人工裁决才能继续的检查点 |
