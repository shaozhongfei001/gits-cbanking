# 背景读本一：系统与业务简介（约 8 分钟）

> 本读本面向不了解项目的委员。读完应能回答：GITS 和 KERT 分别是什么？它们为什么共享一套词汇？为什么词汇归属要委员会来定？

## 1. 业务场景

本项目的业务领域是**银行对公客户经理（RM）的智能工作台**，覆盖对公客户经营的关键旅程：

- **访前准备**：客户经理拜访企业客户前，系统自动汇总客户画像（基本信息、集团关系、日均存款、交易行为、外部舆情）、核查 KYC 缺口、生成候选产品组合与访前报告；
- **拜访与互动**：记录拜访内容，提取客户陈述中的「主张」（如"我们年营收 3 亿"）与「承诺」（如"下周提供财报"）；
- **事实对账**：把客户主张与行内数据、外部数据交叉核验，标注一致/冲突/待核实；
- **受控动作**：任何写回权威系统的操作（建任务、回写 CRM）必须经人工确认、留回执、可审计。

核心设计纪律：**AI 生成的内容一律只是「候选主张」，必须经过人工确认才能成为事实**——这就是系统里大量「主张 / 证据 / 人工门禁 / 受控动作」概念的来源，也是本次词汇表中 19 个运营类概念的由来。

## 2. 两套系统

| | **GITS** | **KERT** |
|---|---|---|
| 定位 | 运营系统（客户经理工作台的业务核心） | 知识工程服务端（独立部署） |
| 技术栈 | Java / Spring（模块化单体） | Python（唯一公共入口） |
| 管什么 | 客户旅程、案头、主张与证据、商机、承诺、人工门禁、受控动作、审计 | 知识地图、知识条目（KI）、技能（Skill）、产品知识卡、激活合同、供给与路由 |
| 类比 | 银行的「业务经办系统」 | 银行的「知识与智库系统」 |

**两系统关系**：GITS 通过标准 HTTP 接口调用 KERT（例如：请 KERT 按知识地图装配访前资料、执行产品推荐技能）。两系统**运行时不互相读取对方的文件或数据库**，只通过接口和「钉住版本的制品副本」协作。

## 3. 为什么共享一套词汇

GITS 说「这个客户的主张需要按知识地图核查」，KERT 说「请给我知识地图 ID 和激活合同 ID」——双方对话中必然出现同一批概念：**客户、产品、知识地图、技能、激活合同、能力、任务类型**……。这批概念的定义（叫什么、有什么属性、彼此什么关系）构成一套**机器可读的共享词汇表**，技术上称为「本体」（详见读本二）。

## 4. 本次要设立的「公共模块」

现状是这套共享词汇表寄居在 GITS 仓库。方案要设立一个**中立的公共模块**（暂名 `public-ontology`）：物理上暂时寄放在 KERT 仓库的一个独立目录，但 Owner、版本线、命名空间、发布流程全部独立，任何时点可以一条命令剥离为独立系统/独立仓库。类比：两家公司合编一本《行业术语词典》，词典编委会独立运作，只是暂时借用其中一家的印刷厂。

## 5. 为什么要委员会裁定

1. **归属权**：客户、产品等 11 个共享概念今后「谁说了算」——这是跨系统的治理权划分，不是技术选型；
2. **合规口径**：方案对国家推荐性标准 GB/T 48000.3-2026 采用「参照适用」（继承通用要求、裁剪专有实体），口径是否恰当需委员会背书；
3. **新设组织资产**：公共模块是未来的独立组织资产，其设立形态（仓内目录 vs 独立仓）与命名空间（是否用中立域名）属架构治理决策。
