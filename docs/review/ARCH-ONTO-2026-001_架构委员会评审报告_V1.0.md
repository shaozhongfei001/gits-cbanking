## 一、正式结论

本次结论为 **RETURN_TO_HLD（退回设计修改后复审）**。

送审包已达到“委员会可以独立阅读并形成架构判断”的基本要求，问题陈述、证据摘录、风险披露、迁移步骤和签署入口均较完整。其工程治理方向也基本正确：类定义与实例权威分离、单一权威、稳定标识、版本钉值、漂移检测、生成物纪律、空转检测和跨仓不直读都应保留。

退回并非否定“三域分治”，而是因为当前 **19/2/11 的具体归属算法、业务对象实例权威、标准符合性表述和批准状态设计存在实质性错误**。这些错误直接落在本次要求委员会裁定的核心范围内，不能通过在决议页附加几条普通条件来消除。

委员会当前可以认可的方向是：

1. GITS 只维护经营过程与受控动作的运行语义；
2. KERT 维护知识、产品知识、规则、地图和技能供给语义；
3. 企业公共语义核心只容纳稳定的跨系统业务身份、角色、基础关系与标识规则；
4. 跨系统执行协议应有独立的集成契约层，不能全部塞入公共业务本体；
5. Kuzu 等图平台只保存经授权的实例投影及查询索引，不成为业务事实或知识审批权威。

## 三、理论判断：哪些成立，哪些不成立

### 3.1 成立的设计原则

| 设计点 | 判断 | 说明 |
|---|---|---|
| 类权威与实例权威分离 | 成立 | T-Box 与 A-Box 可以由不同责任主体维护，但需显式登记并保持可追溯引用。 |
| 每个术语一个定义权威 | 成立 | 同一版本同一术语必须有唯一发布权威；消费方可保存只读、哈希固定的副本。 |
| 跨仓不运行时直读 | 成立 | 有助于可用性、可重复构建和发布隔离。 |
| 哈希钉值与漂移拒绝 | 成立 | 适合作为合同制品控制，但不能替代语义兼容性判断。 |
| SHACL 空转不得当作业务验证通过 | 成立 | 必须增加目标数、覆盖率和夹具门禁。 |
| 生成物不得手改 | 成立 | 源模型、生成配置和生成物必须形成单向可复现链。 |
| 公共模块须防止单系统私有化 | 成立 | 双 Owner、独立版本和独立发布是必要控制。 |

### 3.2 “权威循环”的推导不成立

材料先正确声明“类权威与实例权威允许分离”，随后又把 `Product` 类在 GITS、本体副本在 KERT、产品卡实例在 KERT直接解释为“两仓互为权威”。这三件事本身只形成 **发布依赖和所有权表达不清**，并不自动形成逻辑或治理循环。

真正的循环应满足：A 的发布必须以 B 的权威决定为前提，同时 B 的发布又必须以 A 的权威决定为前提，且没有单向版本契约可以打断。送审包没有提供这样的依赖图。因此 E1 支持“当前归属含混、发布耦合”，不能单独证明“`Product` 必须迁入公共模块”。

需要把“权威循环”改为以下可验证对象：

- 术语定义 Owner；
- 身份与 ID Owner；
- 实例事实 Owner；
- 发布制品 Owner；
- 消费依赖方向；
- 变更审批和兼容性责任。

只有该六列出现闭环依赖，才可以定性为权威循环。

### 3.3 “两侧使用 ⇒ 公共”不成立

§3.2 的判定算法把 A（跨域共享）、B（域引用类）或 C（SSOT 在 KERT）任一满足都归入公共模块。该算法把“被多个系统消费”误当成“必须由双方共同定义”。

一个 KERT 权威的 `KnowledgeMap`、`Skill` 或 `Asset` 完全可以通过版本化契约供 GITS 消费，正如 API 被多个系统调用并不意味着 API 业务对象必须改为公共所有。公共语义核心应满足更严格的条件：

1. 概念在多个业务域中具有相同、稳定、与提供方实现无关的含义；
2. 任一单域都没有充分权力单独改变其语义；
3. 该概念承载跨系统身份、基础关系或互操作语义；
4. 进入公共层能减少耦合，而非把提供方内部模型扩散给所有消费者。

按此标准，`KnowledgeMap`、`Asset`、`Skill` 更接近 KERT 发布的知识供给元模型；`ActivationContract`、`Capability` 更接近集成契约注册表；`TaskType` 更接近受控词表。它们不应因“两侧引用”整体进入公共业务本体。

### 3.4 业务对象和控制面对象被混在同一层

当前公共模块同时容纳客户、法人、集团、产品等业务对象，以及地图、资产、技能、能力、激活合同、任务类型等平台控制对象。这会产生三个后果：

- 企业业务语义与当前 GK-KE 实现结构绑定；
- KERT 内部供给模型的变更被放大为全企业公共本体变更；
- OWL 类、SKOS 词表、JSON Schema 执行合同三种不同治理对象共用一个版本与批准流程。

需要把公共业务语义、知识供给元模型、执行契约注册表和受控词表分开治理，并允许在发布包中组合，而不是在定义层混成一份本体。

### 3.5 `Product` 的身份权威与知识内容权威被混淆

产品知识卡可以是 KERT 的权威知识资产，但这不等于 KERT 产品卡天然成为银行产品身份、产品编码、在售状态和主数据的权威源。建议至少拆为：

- `ProductOffering`：产品身份/编码/生命周期的公共引用对象，A-Box 权威应由产品目录、产品工厂或经批准的数据产品承担；
- `ProductKnowledgeCard`：KERT 权威的知识资产；
- `ProductKnowledgeVersion`：KERT 权威的知识版本；
- `ProductInterpretation`、`RuleBundle`：KERT 权威的解释与规则资产；
- `describesProduct`：知识卡指向产品身份，不以知识卡替代产品主数据。

如果当前试点没有正式产品主数据，只能把 SIM 产品登记表声明为临时模拟权威，并设置退出条件；不能把临时产品卡静默升级为企业产品权威。

### 3.6 客户与法人建模仍不充分

`Customer` 通常是主体在特定机构、关系和时间范围内扮演的角色，不应无条件与 `LegalEntity` 并列为互斥实体。建议公共语义核心至少采用：

- `Party` / `Organization` / `LegalEntity`：主体身份；
- `CustomerRole`：主体在银行关系中的客户角色；
- `EnterpriseGroup`：集团集合或组织安排；
- `GroupMembership`：带来源、有效期和关系类型的关系实体；
- `SourceIdentifier`：来源系统、对象类型、原始 ID 与生效区间。

送审包把 `LegalEntity`、`CorporateGroup`、`GroupRelationship` 的实例权威列为 GITS 运营库，这与“GITS 只维护任务、经营过程、候选结论、人工决定和回执”的既定边界冲突。GITS 最多保存授权快照或运行投影，正式主体与集团关系应由银行源系统/数据平台或明确的数据产品负责。

## 四、对三项待裁定事项的正式意见

### 裁定 1：命名空间

**结论：不采纳“继续以 `https://gientech.com/gits/kno/` 作为新公共模块权威命名空间”的推荐。**

新公共语义核心应使用银行或项目治理主体控制、可长期解析的中立命名空间。具体域名必须由语义架构 Owner 与基础设施/域名 Owner 批准，不得把 `bank.example` 当正式值。

为避免一次性破坏现有 IRI，应采用兼容迁移：

1. 旧 `gits:` IRI 保持只读，进入 `LEGACY`；
2. 新公共术语发布中立权威 IRI；
3. 为逐项术语给出 `oldIRI → newIRI` 映射及语义关系；
4. 只有语义完全相同且身份可互换时才能用 `owl:equivalentClass` / `owl:equivalentProperty`；近似映射用 SKOS 映射或项目自定义映射状态；
5. 经过一个明确的兼容窗口后再退役旧入口。

### 裁定 2：`Product` 类归属

**结论：有条件认可“产品身份引用类进入公共语义核心”，但退回当前定义。**

条件如下：

- 公共层术语改为语义明确的 `ProductOffering`（若保留 `Product`，必须给出等价定义）；
- 产品身份 A-Box Owner 不得默认写成 KERT 产品卡；必须指定产品主数据/数据产品，SIM 阶段可指定临时模拟登记表；
- KERT 只权威维护产品知识卡、版本、解释、规则和证据；
- 40 个悬空引用必须被分类为有效待补、错误引用或作废，不得以永久豁免关闭。

### 裁定 3：公共模块交付形态

**结论：选择独立、受保护的语义契约库；不批准长期寄放在 KERT 根目录。**

允许在初始迁移期使用中性工作区或单独目录制作候选包，但满足下列条件前不得标记为公共权威版本：

- 独立 Owner、版本、发布流水线和访问控制；
- GITS、KERT、数据平台三方评审规则；
- 不依赖 `kert.*` 或 GITS 运行代码；
- 能独立构建、解析、验证和发布；
- 公共术语不因 KERT 内部发布节奏自动变化。

物理仓库不是语义正确性的充分条件，但在当前 6/11 概念实例均由 KERT 管理的情况下，独立库是降低事实私有化风险的必要措施。

## 五、建议采用的目标知识工程架构

### 5.1 四类模型资产

| 资产层 | 典型对象 | 定义 Owner | 实例/记录 Owner | 主要制品 |
|---|---|---|---|---|
| 企业公共业务语义核心 | Party、LegalEntity、CustomerRole、EnterpriseGroup、GroupMembership、ProductOffering、SourceIdentifier | 公共语义 Owner | 银行源系统/数据平台 | OWL/SHACL、词典、ID 与映射规则 |
| KERT 知识供给元模型 | ProductKnowledgeCard/Version、KnowledgeItem、Segment、KnowledgeSource、KnowledgeMapDefinition、SkillDefinition、RuleBundle、EvidenceBundle、Projection | Knowledge Owner/KERT Owner | KERT | OWL/SHACL + 知识资产 Schema/API |
| GITS 经营运行本体 | OperatingCase、Task、Claim、Evidence、Evaluation、Action、Receipt、HumanGate、Interaction、Opportunity、Commitment | Business Process Owner/GITS Owner | GITS | OWL/SHACL + 状态机/动作合同 |
| GK-KE 集成契约注册表 | CapabilityPublication、ActivationContract、EndpointBinding、ConsumerBinding、ContractVersion、TaskTypeScheme | Integration Contract Owner | 契约注册中心 | JSON Schema/LinkML/OpenAPI；需要图查询时生成 RDF 投影 |

### 5.2 权威责任

| 事实类型 | 权威系统 | GITS/KERT 的允许行为 |
|---|---|---|
| 客户、法人、集团、产品身份与正式状态 | 银行源系统/数据平台 | 保存带来源、时点、版本的授权投影，不重新定义真相 |
| 知识文档、规则、知识地图、技能定义、产品知识版本 | KERT | 发布候选、审核版和 ACTIVE 版；不代替业务主数据或审批结论 |
| 任务、案件、建议、人工决定、动作与回执 | GITS | 作为经营过程权威；引用知识版本和源数据时点 |
| 关系查询投影 | Kuzu/图平台 | 提供索引和路径；不得成为知识审批、产品主数据或业务决定权威 |
| 跨系统端点、消费者、版本绑定和兼容性 | 集成契约注册中心 | 双方按批准合同消费；运行时验证版本、权限和状态 |

### 5.3 每个术语必须有的合同字段

重新送审时，每个类、属性、词表项至少应有：

`termId`、权威 IRI、中文/英文名、精确定义、概念类型、T-Box Owner、A-Box Owner、ID Owner、来源系统、生命周期、父概念、域/值域、基数、时间语义、来源/证据、隐私等级、兼容性等级、弃用映射、消费方、验证方式、示例与反例。

### 5.4 本体质量必须由能力问题驱动

当前 R1–R9 主要验证包装、版本和语法，尚不足以证明本体语义正确。每个模块至少要提供一组可执行的 competency questions，例如：

1. 某法人何时、依据哪个源系统成为客户？
2. 某集团成员关系在指定业务日是否有效，来源是什么？
3. 某产品知识卡描述的是哪个产品版本，是否在查询时点有效？
4. 某 GITS 建议使用了哪一版地图、规则、产品知识和数据快照？
5. 某能力可见但不可执行时，原因是未发布、无端点、无授权还是版本不兼容？
6. 某动作由谁确认，产生了什么回执，能否复算当时使用的知识与数据？

每个问题都要绑定查询、正例、负例、预期结果和责任 Owner。只有类数量守恒不能证明语义覆盖。

### 5.5 OWL、SHACL、SKOS 与执行合同分工

- OWL：表达概念、公理、继承和可推理关系；
- SHACL：在指定数据封闭边界内做结构与业务约束验证；
- SKOS：管理任务类型、关系类型、状态码等受控词表；
- JSON Schema/LinkML/OpenAPI：管理跨系统执行合同、字段、端点和错误行为；
- PROV-O 或等价内部模型：表达来源、生成活动、审核人与有效时点；
- Kuzu：物化经过批准的数据投影和关系索引。

不应要求“每个 OWL 类恰好一份 NodeShape”作为普遍真理。Shape 应由验证场景和封闭边界决定；一个类可以有发布、摄取、运行等多个 Shape，不同类也可能复用 Shape。真正必须保证的是目标、约束和场景覆盖可解释且可复现。

## 六、标准与技术规范评审

### 6.1 GB/T 48000.3-2026

国家标准信息平台确认该标准名称、发布日期 2026-01-28、实施日期 2026-08-01 和现行状态；其对象是“标准数字化”中的标准本体。[国家标准信息公共服务平台](https://openstd.samr.gov.cn/bzgk/std/newGbInfo?hcno=25590A00B58C94EE8F675D1A6B01DD5F)

因此本项目可以声明：

> 本项目建立企业本体建模内部规范，并参照 GB/T 48000.3-2026 中经适用性评估确认的通用建模要求。

当前不能声明：

> R1–R9 即为 GB/T 48000.3-2026 的完整继承或符合性要求。

原因是送审包明确承认尚未完成正式文本的条款级核对。R1–R9 中的 SHACL、哈希钉值、每类一 Shape、空转失败、`CODEOWNERS`、影响面分析等大量内容是本项目的良好工程控制，但未证明它们是国标条款要求。正式文本核对完成前，文件名应使用 `REFERENCE-ALIGNMENT.md` 或“参照适用矩阵”，不使用会造成认证印象的“符合性声明”。

### 6.2 OWL 2 版本与导入

OWL 2 允许本体具有 ontology IRI，并可另外具有 version IRI；`versionIRI` 在规范中是 MAY，不是所有本体必须具备的 W3C 强制条件。OWL 导入引用的是可访问的本体文档 IRI，使用 version IRI 固定特定版本是合理的项目策略。[W3C OWL 2 Structural Specification](https://www.w3.org/TR/owl2-syntax/#Ontology_IRI_and_Version_IRI)

因此 R9 应改写为：

> GK-KE 内部发布策略要求生产消费方固定特定 version IRI，并同时校验内容哈希；这是项目加严规则，不宣称为 W3C 或 GB/T 的普遍强制要求。

还应验证 import closure 不同时包含同一 ontology series 的两个不同版本。[W3C OWL 2 Imports](https://www.w3.org/TR/owl2-syntax/#Imports)

### 6.3 SHACL 空转

SHACL 的 `sh:targetClass` 只会选中数据图中该类的实例作为 focus nodes；若没有目标节点，就不会产生该 Shape 的验证结果。规范定义 `sh:conforms=true` 当且仅当没有验证结果。因此“0 目标、0 违规”在 SHACL 本身可以是合规报告，但不能被项目解释为业务覆盖已验证。[W3C SHACL Targets](https://www.w3.org/TR/shacl/#targets)、[W3C SHACL Validation Report](https://www.w3.org/TR/shacl/#validation-report)

项目门禁必须额外记录：

- 每个验证场景的期望目标数和实际目标数；
- 正例、负例和变异测试命中数；
- 无生产实例时的状态为 `NOT_EVALUATED` 或 `DESIGN_ONLY`；
- 豁免只允许继续开发，不得把该项改写为 `PASS`；
- 进入激活门禁前，关键关系必须有经 Owner 批准的实例或受控测试夹具。

## 八、重新送审的最小关闭条件

以下条件全部满足，才可从 `RETURN_TO_HLD` 进入 `PASS_FOR_OWNER_REVIEW`：

1. **逐术语权威矩阵**：覆盖基线 32 类、34 对象属性、1 数据属性和新增 7 类/6 属性；逐项给出模型类型、定义 Owner、实例 Owner、ID Owner、来源、消费者和归属理由。
2. **四层目标模型**：公共业务核心、KERT 知识元模型、GITS 运行本体、集成契约注册表分离；受控词表单列。
3. **业务真相边界纠正**：客户、法人、集团关系、产品身份的正式权威不落在 GITS 经营库或 KERT 知识卡，除非有明确、经 Owner 批准的 SIM 临时权威声明。
4. **`Product` 模式闭合**：产品身份、知识卡、版本、解释、规则之间关系明确；40 个悬空引用有处置清单。
5. **命名空间 ADR**：中立权威 IRI、旧 IRI 兼容映射、解析机制、弃用窗口和碰撞检查完备。
6. **标准适用性矩阵**：基于正式 GB/T 48000.3-2026 文本逐条标注适用、不适用、项目加严和证据；不再把内部控制伪装为标准强制项。
7. **验证状态模型**：明确 `PASS/FAIL/NOT_EVALUATED/DESIGN_ONLY/WAIVED_FOR_DEVELOPMENT`；任何豁免不得满足激活退出标准。
8. **消费者影响清单**：硬编码 ID、旧 IRI、旧文件名、生成目标、plan hash、钉值方全部纳入 Wave 2/3 影响分析。
9. **语义验收矩阵**：至少覆盖身份、有效期、来源、产品卡引用、地图/能力可见与可执行区分、动作回执六类 competency questions，并有正例、负例和预期结果。
10. **新决议页**：委员会只批准设计基线和实施入口；独立 QA、Owner 激活另设门禁，不使用含混的 `APPROVED`。

## 九、下一步允许做什么

在复审通过前，只允许开展不会改变权威制品或运行消费的分析工作：

- 固定三仓/三制品基线和完整哈希；
- 建立术语、消费者、硬编码与悬空引用清单；
- 获取正式标准文本并制作适用性矩阵；
- 起草命名空间 ADR 和旧新 IRI 映射；
- 编制 competency questions 与验证夹具设计；
- 重新估算工作量。

暂不允许：拆分权威本体、改变消费者入口、重钉生产契约、把候选公共模块标成 ACTIVE、签发国标符合性声明或关闭 R-6。

## 十、建议替换 08 签署页的委员会决议文字

> **总体结论：RETURNED / RETURN_TO_HLD。** 方向上认可 GITS 运行本体、KERT 知识本体与公共语义治理分离，认可钉值、漂移检测、生成物纪律和空转门禁。当前版本不批准进入本体拆分与消费切换，原因是公共层判定算法、客户/法人/集团/产品实例权威、标准符合性表述及批准状态模型存在阻塞缺陷。项目组可立即开展只读基线、术语权威矩阵、消费者扫描、标准条款适用性核对和命名空间 ADR；完成本报告第八节十项关闭条件后重新提交架构委员会。委员会本次决定不构成实现完成、QA 通过、Owner 激活或生产可用证明。
