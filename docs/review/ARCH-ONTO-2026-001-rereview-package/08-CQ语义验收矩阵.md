# 语义验收矩阵：六类 Competency Questions（关闭条件 9 / M-07）

> 每 CQ 绑定：验证对象 → 查询（形态）→ 正例 → 负例 → 预期结果 → 责任 Owner → 变异复验。夹具落地为实施阶段工作；本表为设计基线。**关键关系在 D2 未决期间状态 = NOT_EVALUATED（见 06 号文件 §4）**。

## CQ1 身份与来源：某法人何时、依据哪个源系统成为客户？

| 项 | 内容 |
|---|---|
| 验证对象 | `CustomerRole` + `SourceIdentifier`（L1） |
| 查询 | 按 LegalEntity 查 CustomerRole 及其 SourceIdentifier（sourceSystem/objectType/originalId/validFrom）（SPARQL 或 L1 图投影查询） |
| 正例 | 法人 LE-001 经 `SourceIdentifier{EDWCRM, Customer, C001, 2026-01-05}` 关联 CustomerRole CR-001 |
| 负例 | CustomerRole 无 SourceIdentifier ⇒ 摄取拒绝（fail-closed） |
| 预期结果 | 正例返回（成为客户的时点 2026-01-05 + 来源 EDWCRM）；负例具名拒绝 `MISSING_SOURCE_IDENTIFIER` |
| Owner | 公共语义 Owner（A-Box 待 D4） |
| 变异 | 删除 SourceIdentifier 的 sourceSystem ⇒ 必须 FAIL |

## CQ2 关系有效期：某集团成员关系在指定业务日是否有效，来源是什么？

| 项 | 内容 |
|---|---|
| 验证对象 | `GroupMembership`（validFrom/validTo + 来源） |
| 查询 | 按（fromEntity, toEntity, 业务日 D）查有效 GroupMembership 及来源 |
| 正例 | M-001（2025-06-01~2026-12-31，来源=集团登记系统），D=2026-09-20 ⇒ 有效 |
| 负例 | 同一对实体在 D=2027-01-01 查询 ⇒ 无效（过期不得返回有效） |
| 预期结果 | 正例返回有效+来源；负例返回无效且不带「有效」标记 |
| Owner | 公共语义 Owner（A-Box 待 D4） |
| 变异 | 把 validTo 改到查询日之后 ⇒ 负例翻正必须被检测为变更 |

## CQ3 产品卡引用：某产品知识卡描述哪个产品版本，查询时点是否有效？

| 项 | 内容 |
|---|---|
| 验证对象 | `ProductKnowledgeCard` —describesProduct→ `ProductOffering`；`ProductKnowledgeVersion` 有效期 |
| 查询 | 按卡 ID 查 describesProduct 目标 + 当前有效版本（SPARQL/L2 投影） |
| 正例 | 卡 PROD-CB-001 → ProductOffering PROD-CB-001，有效版本 v3（查询日在有效期内） |
| 负例 | 卡指向已退役版本 / 悬空 product_id（40 处悬空引用样本）⇒ 具名提示 `DANGLING_PRODUCT_REF` |
| 预期结果 | 正例返回产品身份+版本；负例具名拒绝或标记，**不得静默通过** |
| Owner | Knowledge Owner（A-Box 待 D2；**D2 未决期间本 CQ 关系场景 = NOT_EVALUATED**） |
| 变异 | 将 describesProduct 改指不存在的产品 ⇒ 必须 FAIL |

## CQ4 版本可重放：某 GITS 建议使用了哪一版地图、规则、产品知识和数据快照？

| 项 | 内容 |
|---|---|
| 验证对象 | ActivationPlan（planHash + 版本子块：KM/AC/本体/数据快照） |
| 查询 | 按建议 ID 取 ActivationPlan，重算 planHash 并核对版本子块（API + 哈希重算脚本） |
| 正例 | 建议 S-001 的 planHash 重算一致，版本子块含 KM@v、AC@v、ontology@sha256:…、snapshot@v |
| 负例 | 版本子块缺 ontology 字段 ⇒ 拒绝执行（fail-closed，沿袭 ADR-0016） |
| 预期结果 | 正例可完整回答「哪一版」；负例具名拒绝 `PLAN_VERSION_INCOMPLETE` |
| Owner | Integration Contract Owner |
| 变异 | 篡改版本子块任一字段 ⇒ planHash 必须不一致 ⇒ FAIL |

## CQ5 能力可见与可执行：某能力可见但不可执行时，原因是什么？

| 项 | 内容 |
|---|---|
| 验证对象 | `CapabilityPublication` + `EndpointBinding` + `ConsumerBinding` + `ContractVersion`（L4） |
| 查询 | 按能力 ID 取四对象状态，判定原因类别（API/注册中心查询） |
| 正例（四态各一） | ① 未发布（status=DRAFT）② 无端点（无 EndpointBinding）③ 无授权（ConsumerBinding 缺失/过期）④ 版本不兼容（ConsumerBinding 版本 ∉ 兼容集） |
| 负例 | 四种原因混报为单一「不可用」⇒ FAIL |
| 预期结果 | 每种场景返回**可区分**的原因码（`NOT_PUBLISHED`/`NO_ENDPOINT`/`UNAUTHORIZED`/`VERSION_INCOMPATIBLE`） |
| Owner | Integration Contract Owner |
| 变异 | 删除 EndpointBinding ⇒ 原因必须从 OK 变为 NO_ENDPOINT |

## CQ6 动作与回执：某动作由谁确认，产生什么回执，能否复算当时使用的知识与数据？

| 项 | 内容 |
|---|---|
| 验证对象 | `Action`/`Receipt`/`HumanConfirmation`（L3）+ planHash 复算 |
| 查询 | 按 action_id 查确认人、回执、关联 plan 并重算（API + 复算脚本） |
| 正例 | Action A-001 ← HumanConfirmation{actor=RM-007, decision=APPROVE} → Receipt{status=SUCCESS}，planHash 复算一致 |
| 负例 | 无 HumanConfirmation 的 Action ⇒ FAIL（违反「AI 候选未经人工确认不得执行」） |
| 预期结果 | 正例完整回答确认人/回执/可复算；负例具名失败 `ACTION_WITHOUT_CONFIRMATION` |
| Owner | GITS Owner |
| 变异 | 删除 HumanConfirmation 记录 ⇒ 必须 FAIL |

## 门禁接线

- 六 CQ 场景进 `make conformance`（实施阶段），目标数与命中数按 06 号文件 §1 记录；
- 激活门禁（OWNER_ACTIVATED）：六 CQ 全部 `PASS` 且实际目标数 > 0；CQ3 受 D2 硬阻塞（见 06 §4）；
- 每 CQ 配变异用例，进全量变异回归矩阵。
