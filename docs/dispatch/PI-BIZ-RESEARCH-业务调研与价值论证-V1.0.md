## 0. 结论先行

**PC2（八章产品解读）的业务必要性，取决于三个业务事实是否成立：**

| 编号 | 业务事实 | 若不成立的后果 |
|---|---|---|
| `BF-1` | 客户经理**会**在方案/对客沟通中引用产品口径，而引用的必须是**当前有效版本**（否则出错） | 版本时效与阻断无业务价值 |
| `BF-2` | 客户经理**会**遇到"不能承诺但容易被追问"的场景（额度/期限/利率/费用/担保/时效） | 不可承诺清单与话术边界无业务价值 |
| `BF-3` | 存在**事后追溯**需求（合规/审批/内部抽查问"这个说法凭什么"） | 证据回链与版本快照无业务价值 |

**在这三条事实上的可用证据**：`BF-1` 有仓库内**业务剧本**的明确要求（见 §4 `F1`）；`BF-2` 有需求包业务规则 + 外部监管口径支撑；`BF-3` 有需求包成功标准支撑（见 §2、§3）。

**若这三条事实成立 ⇒ PC2 的必要性成立，且 P0 不是"八章齐备"，而是四项承载能力**：版本时效与阻断、待核验状态、不可承诺清单、证据回链。
**若这三条事实不成立 ⇒ 我的建议是"不做 PC2"，只对 P38 做定向增强**（§6 `H6` 是证伪判据）。

## 2. 业务问题陈述（来自 `S-A`，原文口径）

需求包 `01` §2.1 给出的四条业务目标：

1. 让客户经理**不依赖口口相传**，准确理解一个产品：是什么、解决什么问题、如何办理、需要什么材料、价格如何形成、协议约束是什么；
2. 将产品口径与**制度、规程、价目、协议模板**绑定，降低**过时、错误和无依据解释**；
3. 将"客观产品解读"与"针对客户的产品体检/推荐"**分离**，避免客户上下文污染产品知识；
4. 为拜访、方案编制、客户体检与受控推荐提供**可引用、可追踪、可复核的已发布产品知识版本**。

§2.2 成功标准中的可判定项：一个详情页内完整理解产品（不必跳转多个制度库）；每条重要条款**可定位证据或明确标记待核验**；页面**不出现**适配分/推荐理由/授信结论/价格承诺；**版本、审核、责任人、复审日期清晰可见**。

归纳为三个业务问题：

| 编号 | 业务问题 | 来源 |
|---|---|---|
| `BP-1` | 口径获取依赖口口相传 ⇒ 过时、错误、无依据解释 | `S-A` §2.1-1/2 |
| `BP-2` | 口径与制度/价目/协议脱钩 ⇒ 无法追溯、无法复核 | `S-A` §2.1-2/4、§2.2 |
| `BP-3` | 客观解读与客户推荐混同 ⇒ 越权承诺与上下文污染 | `S-A` §2.1-3、`S-B` `PI-BR-003/008/011` |

**外部口径（`S-D`）**：
- 《商业银行服务价格管理办法》：商业银行应严格执行**明码标价**制度、充分披露服务价格信息（价格口径不得随意口头给出）；
- 《银行保险机构消费者权益保护管理办法》第二十三条：不得进行**欺诈、隐瞒或者误导性的宣传**，不得夸大产品收益或服务权益、掩饰产品风险（⇒ "不能说的话"必须前置约束，而不仅是事后追责）。

## 5. 对照：P38 现状 vs PC2 目标（以 `S-A`/`S-B`/`S-C` 为尺子）

| 尺子（业务要求） | P38 现有承载 | PC2 目标承载 | 差距性质 |
|---|---|---|---|
| `F1` 版本时效与阻断 | 仅 `isStale` 一个布尔位；无"失效版本仍可审计、不可用于方案"的结构 | 版本状态 + 有效期 + 阻断 + 历史可审计 | **无承载位**（P38 数据模型缺位） |
| `F2` 不可承诺清单与话术边界 | 无 | 常驻"可说/不可承诺"两组话术 | **无承载位** |
| `F3` 每条款证据/待核验 | 字段级证据（存在），但仅覆盖少量字段且无"待核验"呈现规则 | 条款级证据 + 待核验状态 | 部分具备，需扩展 |
| `F4` 版本/审核/责任人/复审可见 | 无（只有 releaseId） | 治理栏：基准日/生效日/复审日/审核记录/责任人 | **无承载位** |
| `F5` 非推荐约束 | 无明显推荐元素（符合） | 同 | 已满足 |
| `F6` DEMO 标识与阻断 | 页面有"演示"提示 | 标识 + 生产发布阻断 | 部分具备 |
| 「看原文」 | **强项**：原文全文可读 | 原文作为**证据溯源**（不再作为内容主体） | P38 在此项不弱 |

**判读**：P38 在"查阅原文"上并不弱；它在 `F1`/`F2`/`F4` 三类失败模式上**没有承载结构**——这不是内容多少的问题，是数据模型里没有这些位置。

**反方（必须写明）**：若业务上 `F1`/`F2`/`F4` 的风险实际不发生（客户经理只用当前版本、只按价目表口径说话、没有事后追溯需求），则 **PC2 不必要**，P38 足够，正确动作是增强 P38（可搜索、原文定位、版本标识）。

## 6. 价值假设与可测指标（因无法访谈，用可证伪假设替代签字）

| 编号 | 价值假设 | 可测指标 | 证伪方法 |
|---|---|---|---|
| `H1` | 版本时效阻断能防住"用失效版本做方案" | 构造失效版本用例 → 必须阻断；漏放数 = 0 | 人为把阻断关掉 → 用例必须变红（变异测试） |
| `H2` | "待核验"机制能防住无依据解释被当结论用 | 抽掉某字段证据 → 该字段必须显示待核验；无证据字段显示为确定值的数量 = 0 | 注入"无证据但有值"的字段 → 必须被标记为待核验 |
| `H3` | 不可承诺清单能覆盖客户最常追问项 | 覆盖 额度/期限/利率/费用/担保/时效 六项 = 100% | 移除任一项 → 页面出现可被误读为承诺的表述 |
| `H4` | 证据回链可达 | 任一结论 ≤1 次点击可到证据与来源 | 找不到证据路径的结论数 > 0 即证伪 |
| `H5` | 下游引用不串版 | 引用必须携带 `published_version_id` + `evidence_snapshot_id`；缺失即拒绝 | 构造不带版本的引用 → 必须被拒绝 |
| `H6` | **（证伪 PC2 的判据）** 若 `H1`~`H4` 全都不做，页面与 P38 无实质差别 | 若去掉这四项后，页面对 `F1`/`F2`/`F4` 的承载与 P38 等同 ⇒ PC2 无独立价值 | — |

## 7. 给台阶 3（设计）的硬约束输入

1. **`BF-1` 承载**：版本状态机必须支持"已废止版本可审计查看、但不可用于当前方案"，且阻断必须有可测用例（`H1`）；
2. **`BF-2` 承载**：不可承诺清单为**页面常驻**元素，不得折叠隐藏；每项附"可以说的话"（`PI-BR-004`）；
3. **`BF-3` 承载**：所有结论携带 `published_version_id` + `evidence_snapshot_id`；缺失视为不合格（`PI-BR-010`）；
4. **诚实性**：无证据一律"待核验"（`PI-BR-005`）；DEMO 常驻标识 + 生产阻断（`PI-BR-009`）；
5. **不做**：任何适配度、推荐排序、胜率、下一最佳行动（`PI-BR-003/008`）。
