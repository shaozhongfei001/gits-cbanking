## 0. 结论速览

**一句话**：三层各自都跑得通，但把它们真正"打穿"的那条链上，**有 4 处断点 3 处同名异义**；
其中 2 处直接阻塞 GK17 §5 的验收判据 **V1/V3**，另外 5 处是静默漂移面（"错了但门禁不红"）。

| # | 断点 | 严重度 | 是否阻塞 V1–V4 | GK17 现有波次覆盖 |
|---|---|---|---|---|
| **D1** | 语义查询执行链在生产**零装配**，守卫只返回占位行数 | **BLOCKER** | 阻塞 **V1**（"本体查实体/关系"无真实输出） | ❌ 未覆盖 |
| **D2** | A-Box（13 个产品个体）**未被任何装配加载**，运行期只加载 T-Box（0 个体） | **BLOCKER** | 阻塞 **V1/V3**（无个体可查、无对象可锚定） | ⚠️ W3 已产出、**装配未闭合** |
| **D3** | 语义查询 ID `SQ-*` 是"第 4 处表示"，**无权威源、无门禁**（Java 硬编码 9 = 合同声明 9，恰好一致） | **MAJOR** | 影响 **V4** 同族（静默漂移） | ❌ 未覆盖（W5 只做"地图/本体/投影"三处） |
| **D4** | **两套 `KnowledgeMap` 合同并存**，必填字段交集只有 3 个；图结构（nodes/edges）**无 Java 领域模型** | **MAJOR** | 影响 V1 的"地图按结果定向激活" | ⚠️ 方向未裁定 |
| **D5** | 地图域对象在 HTTP 层**不可达**（`mapPort` 注入但零使用）；"知识地图"在 API 层对应**三个不同东西** | **MINOR**（同词多义 → 可升 MAJOR） | 不阻塞 | ❌ 未覆盖 |
| **D6** | 图侧查询 ID（`SIM-GQRY-*`）与语义侧（`SQ-*`）**两套命名空间、零映射** | **MAJOR** | 影响 V4 同族（"同词两义"） | ❌ 未覆盖 |
| **D7** | 语义层**能力错位**：`SemanticRepositoryPort` 有真实 Jena 实现但生产零装配；`SemanticQueryPort` 有守守卫无真实实现 | **MAJOR** | 与 D1 同源 | ❌ 未覆盖 |

**最危险的形态**（对齐论证 §A.3）：D3 + D4 + D6 都是**静默**的——地图合法、本体合法、计划合法、门禁不红，
但"计划里带着一个必然被 DENY 的查询 ID"或"地图与合同说的不是同一个地图"这类错误**不会被任何现有门禁发现**。

## 4. 断点详述（含静默失败形态）

### D1 [BLOCKER] 语义查询执行链在生产零装配

- 事实：F-05 + F-07。守卫与真实实现**都只存在于模块与测试中**；`apps/api`、`apps/worker` 无任何 Bean。
- 后果：`ActivationPlan.semanticQueries`（合同必填，F-04）里写着 5 个查询 ID，**运行期没有任何组件能执行它们**。
  计划是"声称要查什么"，系统是"没人能查"。
- 静默形态：不会报错——没有任何调用点，就没有任何失败点。指标全绿。

### D2 [BLOCKER] A-Box 未被装配加载

- 事实：F-08 + F-09 + F-10。装配只读单个 `gits-core.owl.ttl`（T-Box，0 个体）；
  W3 产出的 `products.ttl`（13 个体）**零代码引用**。
- 后果：即使 D1 修好，真实 Dataset 里也**没有个体**可查；**V3 反例（地图引用不存在的个体必须 fail-closed）连"存在的个体"样本都没有**。
- 与 V1 冲突：V1 要求"本体查实体/关系"，当前实体数 = 0。

### D3 [MAJOR] `SQ-*` 是"第 4 处表示"，无权威源、无门禁

- 事实：F-06 + F-15 + F-16。`SQ-*` 的**唯一"权威"是 Java 硬编码常量**；合同侧只有字符串引用；
  GK-KE 有 `QueryDefinition` 合同却**零实例**；**全仓无脚本校验**三方一致。
- 现状：9 = 9（我实测，恰好一致）。**恰好一致 ≠ 受保护**：任何人给 `AC-*` 增一条 `SQ-*`，
  计划会带上它，运行期必然 DENY（一旦 D1 修好），而**门禁全绿**。
- 定位：这正是论证 §A.5 约束①的缺口——"一条事实只有一个地方能改"，而 `SQ-*` 事实有 **3 个地方**能改且无人校验。
- 与 GK17 W5 的关系：W5 三处一致性 = **地图 / 本体 / 投影**（`loops/GK17-ontology-unified-map/memory/waves/W5-PLAN.md:13`），
  **不含**"合同/技能声明 ↔ 运行时登记表"。所以这是**第 4 处**，属增量。

### D4 [MAJOR] 两套 `KnowledgeMap` 合同，交集 3 字段；图结构无 Java 模型

- 事实：F-01 + F-11 + F-18。`CTR-KMAP-001`（导航文档模型）与 GK-KE `KnowledgeMap`（图模型：`nodes/edges/entryNodes/releaseId/simulationOnly`）
  概念同名、字段几乎不交；**Java 只实现前者**，后者的图结构在实现侧**不存在载体**。
- 后果：论证 §4 说"地图负责去哪找"——**当前实现里的"地图"是 `domains` + `assetRefs` 字符串**，
  没有"节点/边"可被本体查询结果定向驱动。V1 的"地图按（本体查询）结果定向激活资产"因此在实现侧缺乏对象模型。
- 静默形态：两份 schema 各自合法、各自生成物存在，`make check` 绿；只有人对比字段时才会发现。

### D5 [MINOR] "知识地图"在 API 层有三个不同所指

- 事实：F-12 + F-13。`mapPort` 注入零使用 ⇒ `KnowledgeMap` 域对象**无 HTTP 出口**；
  `/api/v1/knowledge/map` 实际是"元素分组"；`/customer/{id}/knowledge-map` 是"装配视图"；前端 `KnowledgeMapView.vue` 另有其消费。
- 后果：前端/联调讨论"知识地图接口"时**指代不确定**——与论证 §A.2"同词两义"同族，只是发生在 API 命名层。

### D6 [MAJOR] 图侧与语义侧两套查询 ID 命名空间，零映射

- 事实：F-14 + F-06。`SIM-GQRY-001/002`（有 `maxHops`/`maxNodes` 上界声明）vs `SQ-*`（9 个，无上界声明）。
- 后果：两条检索通道（Kuzu 图侧 / Jena 语义侧）都声称"有界/受控查询"，但**没有统一登记处**，
  谁有界、谁无界、二者能否互相替代**在合同层无定义**。属"同一件事两个名字"。

### D7 [MAJOR] 语义层能力错位

- 事实：F-07。`SemanticRepositoryPort` 有**真实** Jena 实现（加载 + SHACL 校验）但**生产零装配**；
  `SemanticQueryPort` 有**守卫**但**无真实实现**。
- 后果：语义层当前是"**能校验、不能查**"，而 V1 需要的恰好是"能查"。
  能力在两个端口间**正好错位**，且两侧都未接入生产。
