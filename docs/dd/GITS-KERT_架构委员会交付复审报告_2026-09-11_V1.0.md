## 3. 架构内容评审

### 3.1 理论与责任边界

C01 对“谁定义、谁保管、谁执行”做了对象级划分：公共语义核心管理共享类型与身份规则；银行源保管客户、账户、交易和正式业务事实；分析语义模块管理指标与受控查询；KERT 管知识资产、认定、发布和任务知识地图；GITS 管经营任务、建议、人工决定、动作及回执；Kuzu 仅承载可重建投影。

该划分符合单一权威、多视图投影原则，也正确区分类型、实例、断言、检索表示和业务决定。开放信息假设、三值规则、事实与观点分离、知识审批与业务动作审批分离，能够经受知识表示与银行责任边界的理论检验。

**结论：D 阶段通过。** 后续 L0 必须对现行 P20/DKES/PI-0 和实际字段逐项映射，本包没有宣称已完成迁移。

### 3.2 注册中心与知识地图

C02 明确内容知识图、任务知识地图和运行依赖图三种视图；定义 AssetCatalog、SourceRegistry、CapabilityRegistry、QueryRegistry、MapRegistry、ReleaseRegistry 六个逻辑模块；规定 discover → expand → plan → execute 的渐进披露和确定性激活过程。

样例提供 KnowledgeMap、AssetVersion、Capability 合同、Query 注册和 ActivationPlan，并检查引用闭包、缺失依赖、执行环和 planHash。地图没有被误用为“把内容图路径直接变成工具调用序列”。

**结论：D 阶段通过。** 当前模拟校验将 Capability 的可发现身份同时登记为 PROCESS_TOOL AssetVersion，并另存 Capability 合同；I 阶段应补 Capability/Query/Source/Release 的正式 Schema 与服务探针，避免资产可见性和能力可执行性混为一个状态。

### 3.3 非结构化知识自动构建、审核和发布

C03 的 P01–P10 流水线覆盖原文接入、结构解析、候选断言、身份对齐、候选地图、冲突与差异、双维人工认定、编译验证、不可变发布及撤销。内容认定和任务地图用途认定分开，审批绑定版本/hash/用途；发布需要投影 ready、CAS 当前指针和 outbox。

包内验证了原文 quote/hash、无原文句子拒绝、内容认定缺少地图认定拒绝、审批后改字拒绝、自审拒绝和半发布拒绝。

**结论：D 阶段通过。** 模拟 ReviewDecision 只是夹具；真实身份、签署、CAS、outbox、撤销即时性和候选/发布索引隔离仍是 I 阶段验收项。

### 3.4 分析语义服务

C04 正确定义了指标 Owner、对象与粒度、时间、币种、快照、映射、权限和受控查询编译。日均案例以账户日唯一记录为基础，拒绝交易关联放大、缺日、重复粒度和无政策的跨币种聚合；明确禁止 `SUM(DISTINCT balance)` 修补重复关联。

包内有 MetricDefinition、SemanticRequest/Result、QueryRegistry、参数化 SQL 和确定真值；校验器覆盖 C001 日均、同余额两账户、跨币种、缺日、重复账户日、机构谓词以及额度与可提款金额分离。

**结论：D 阶段通过。** 14 个 Schema 是最小交换剖面，无法表达 C04 正文列出的全部生产字段；这在 README 中已披露。L0-2/L2-1 必须补全 OpenAPI、MetricDefinition 生产剖面、授权票据、joinCardinality、sourceSnapshotPolicy 和复算接口，不能直接以当前最小 Schema 激活生产合同。

### 3.5 既有 RAG、GraphRAG 与 Kuzu

C05 的取舍合理：保留既有向量 RAG；LightRAG 只作为可关闭试验；Kuzu 是 KERT 内部可重建的隔离图投影；三者均不承担注册和知识审批权威。A/B/C 试验把“注册/地图治理收益”和“图增强增益”分开，避免用 A→C 的总差异冒充 GraphRAG 收益。

**结论：D 阶段通过。** Kuzu、LightRAG 和 ExistingRagAdapter 均未集成，当前状态如实。LightRAG 不阻断基础经营闭环；Kuzu 图接口验证按 C08 L5-1 实施。

### 3.6 GITS—KERT 运行闭环

C06 明确计划、证据、三值判断、受控动作、执行前权限/版本复核、幂等与结果未知后的对账。KERT 不执行 GITS 正式业务写回；模拟动作白名单只允许创建跟进任务和记录接触结果。

**结论：D 阶段通过。** API 表和 14 类核心 Schema足以作为候选设计输入，但不构成完整 OpenAPI，也没有服务级权限、恢复或消费者测试。36 项验收矩阵对此均标记为 `PLANNED_NOT_EXECUTED`，状态诚实。

### 3.7 模拟数据与验收治理

C07 的“大模型生成业务内容、确定性程序派生数值、独立算法复算”方法正确。正常数据、负例与 oracle 分离；数据和文档均有 SIM 标识，不伪造真实银行、研究机构或外部模型调用记录。

C08 提供 CR-01–08、L0–L6 实施顺序、36 项验收计划和角色分工。全部 T01–T36 当前均为 `PLANNED_NOT_EXECUTED`，未将离线校验冒充服务验收。

**结论：D 阶段通过。** 合同候选可以进入 Owner 审议和 L0 适配，不能据此跳过现状定位、兼容性对照或独立 QA。

## 5. 本轮新发现与必改项

### AC-01｜MAJOR｜当前 ZIP 尚未形成单一封版控制集合

**已确认事实：** 目录 120 个文件，MANIFEST 117 条；完整总契约和后补 `negative_cases.json` 未列入 MANIFEST。校验器也不校验顶层 MANIFEST。按 README 再生成后，自检变为 126/0，并改变 dataset manifest/self-check。

**风险：** 同一个 ZIP 同时存在“117 个受控文件”“120 个受控文件”“125 项自检”和“再生成后 126 项自检”四种口径。每个数字在局部都能解释，但不适合作为正式签署对象。

**整改：** 发布 `GK-KE-CONTRACT-V1.0.1_REVIEW.zip` 或同等新候选版本；将除 MANIFEST 自身外的全部包内文件纳入 MANIFEST，或明确附件边界；更新 dataset manifest、自检结果和 README；校验器新增 MANIFEST 路径、size/hash、未登记文件及重复路径检查；固定新 ZIP hash。

**关闭标准：** 解压后“目录文件集合 − 明确排除项 = MANIFEST 集合”，一次完整构建后工作树无差异，自检数与落盘结果一致。责任：交付 TL / 制品维护者。

### AC-02｜MAJOR｜汇报中的补充脚本和 20/40 结果没有随提交材料交付

**已确认事实：** 汇报声明 `scripts/gk_ke_contract_examples.py` 为 20 正例/40 负例、`tools/verify_simulation.py` 可独立复算；ZIP 中均不存在。ZIP 实际生成器输出 14 正例/28 Schema 负例。`negative_cases.json` 还引用了未随包提供的 `verify_simulation.py`。

**风险：** 架构委员会不能根据 ZIP 复现补充结果，汇报把仓库外证据写成了包内可复核能力。

**整改：** 二选一：将脚本、输入、依赖和原始结果纳入受控包并写入 MANIFEST；或从本次交付汇报中删除 20/40 与独立脚本声明，只保留已复现的 14/28 和校验器内指标复算。若 40 指业务负例而非 Schema 文件，必须给出唯一 caseId、分类和实际执行状态，不能混用“负例文件数”和“被拒测试数”。

**关闭标准：** 委员会仅按包内 README 即可复现所有宣称结果。责任：Feature Pilot / TL。

### AC-03｜MAJOR｜Git HEAD 与独立 QA 声明未形成可核验链

**已确认事实：** 用户提交说明写当前 HEAD `0034f22`；汇报 §1.1 写权威目录 HEAD `3e0d741`，§5 表格又将 `a40de1b` 标为当前 HEAD，并引用 `36f18eb`、`91d5fed` 的 QA/交付关系。ZIP 不含 Git 元数据、提交清单、tree hash、diff 或 QA 报告。包内 `CONTRACT_INDEX.json` 与自检结果仍标记 `independentQa=NOT_PERFORMED`。

这些状态并不必然互相冲突：QA 可以发生在作者自检之后，HEAD 也可以继续前移。但当前材料没有说明每个提交的父子关系、QA 的受测 HEAD，以及最终 `0034f22` 是否只增加说明而未改变受测制品。

**风险：** 无法签署“ZIP 等价于 Git 权威目录”或“最终 HEAD 独立 QA_PASS”。

**整改：** 提交以下最小证据：

- 分支、最终 HEAD、`git log --oneline --decorate` 和受控目录 tree hash；
- ZIP 根目录相对文件与 Git 目录的逐文件 hash 对照；
- 独立 QA 报告，包含 QA 主体、受测 HEAD/tree/ZIP hash、命令、环境、实际结果、缺陷与复测；
- 说明 QA 后的每个提交是否触及受测目录；触及则重跑，未触及则给出 diff 证明；
- 保持包内作者自检的 `independentQa=NOT_PERFORMED` 也可以，但汇报须明确“这是作者报告字段；独立 QA 证据位于何处”。

**关闭标准：** 一个最终 HEAD、一个受控 tree、一个 ZIP hash、一个对应 QA 结论形成一一对应关系。责任：Tech Lead / 独立 QA。
