## 0. 交接结论

当前会话已经完成一套银行通用、可落地填写、支持专家协同并具备实施闭环的《对公客户首次拜访与综合服务建议书标准模板》V1.0，同时形成“五表联动作业工作簿”。其核心不是把银行产品堆叠成清单，而是把第一次拜访组织成一条可追踪的客户经营链：

> 公开信息与内部信息准备 → 形成可核验的经营假设 → 首次拜访确认目标、事件、痛点、根因、决策链和时间窗 → 将需求转译为服务主线 → 由产品经理和专业专家联合设计主方案、备选方案、前置条件与风险控制 → 完成内部审批 → 以客户语言交付建议书 → 用30/90/180天计划推动实施和复盘。

1. 文档控制、使用边界、双版本原则、五闸门和事实状态标签；
2. 拜访前客户经营假设简报；
3. 首次拜访纪要与需求核验；
4. 对客版综合服务建议书母版；
5. 客户与行业诊断、需求—方案—产品总览、总体服务蓝图；
6. 可复制的分项服务设计卡与三层组合包；
7. 客户价值测算、风险与适用条件、30/90/180天实施路线图；
8. 客户信息采集表、行业分析表、需求—方案—产品映射表、专家协同单、30/90/180天实施计划五张配套表；

## 1. 本会话任务起点与目标

### 1.1 用户设定的业务角色

本次工作的角色视角是“对公王牌客户经理”。第一次拜访客户时，客户经理不能只掌握工商信息或账户授信信息，而要做到：

- 对客户形成尽可能全面的认识；
- 对客户所处行业、细分赛道、价值链、竞争和风险有清晰判断；
- 能够针对客户的战略目标、经营事件、业务痛点和决策机制定制服务；
- 服务建议不局限于单个金融产品，可由客户经理牵头，联合产品经理和专业对公金融专家团队共同输出；
- 最终交付既可以是专业服务建议，也可以是产品组合包，还必须具备推进、实施、复盘和责任闭环。

### 1.2 用户最初提出的研究方向

用户要求全面搜索、查找银行对公客户服务建议书，主要研究对象应包括：

- 国有大型银行；
- 全国性股份制银行；
- 资产质量较优、对公经营能力较强的城市商业银行。

研究目的不是简单收集同业材料，而是吸收银行客户经营、综合金融服务、行业服务和一户一策方案中的有效结构，形成可复制的标准模板。

### 1.3 用户最终明确的交付物

用户最终要求形成：

1. 《对公客户首次拜访与综合服务建议书标准模板》；
2. 客户信息采集表；
3. 行业分析表；
4. 需求—方案—产品映射表；
5. 专家协同单；
6. 30/90/180天实施计划；
7. 将上述内容转换为可持续复用的“写作模块”。

本会话实际交付采用“双载体”设计：

- Word：承载方法、写作结构、会议准备、客户诊断、方案表达、控制规则和全部附录表单；
- Excel：承载高频作业录入、统一ID、跨表联动、公式计算、状态校验、逾期提示和阶段统计。

## 2. 研究和设计中形成的核心判断

### 2.1 建议书的本质

“客户服务建议书”不是产品宣传册、授信方案书或客户尽调报告的替代品。它是客户经营过程中连接“理解客户”和“推动落地”的中间载体，必须同时具备五种属性：

| 属性 | 具体含义 |
|---|---|
| 客户理解载体 | 体现银行对客户战略、经营目标、关键事件、价值链、现金流和风险的理解 |
| 需求确认载体 | 将客户表述、银行判断、待核验假设和优先级明确分开 |
| 专家协同载体 | 让客户经理、行业专家、产品经理、风险合规等围绕同一需求共同设计 |
| 对客沟通载体 | 使用客户语言表达价值、路径、条件和责任，避免内部术语直接外溢 |
| 实施管理载体 | 将建议转为阶段目标、责任人、里程碑、KPI、证据和复盘机制 |

### 2.2 首次拜访不能以产品推销为起点

模板明确采用“从战略到交易”的访谈顺序。客户经理首先要确认：

1. 未来12—24个月经营目标；
2. 决定成败的关键事件和时间窗口；
3. 增长、效率、现金流、风险或治理方面的优先问题；
4. 采购、生产、库存、销售、回款等价值链环节中的资金占用和波动；
5. 主要客户与供应商的账期、结算方式、币种和集中度；
6. 现有银行合作体验和选行标准；
7. 资本开支、并购、重组、上市、发债、出海、员工激励等事项；
8. 需求提出人、评估人、审批人、使用人、预算、内部流程和材料条件。

只有在目标、事件、根因、影响、决策链和期限清楚后，才能讨论融资、结算、现金管理、供应链金融、跨境、投行、数字化等产品和服务。

### 2.3 从“客户360”转为“三张经营图”

首次拜访准备不是追求无限堆叠字段，而是至少形成三张可行动的图：

| 图谱 | 核心对象 | 需要回答的问题 |
|---|---|---|
| 客户图谱 | 集团、母子公司、实际控制人、核心子公司、上下游、生态伙伴 | 客户是谁，集团与生态边界是什么，价值和风险集中在哪里 |
| 关系图谱 | 决策人、影响人、使用人、把关人、我行覆盖关系、联系频率 | 谁决定、谁影响、谁使用、谁否决，我行关系缺口在哪里 |
| 业务图谱 | 商流、物流、资金流、信息流、账户、币种、期限、高频场景 | 钱从哪里来、到哪里去，何时波动，哪一环最需要服务 |

### 2.4 客户信息必须带状态，而不能把推断写成事实

模板建立了六类状态标签：

- `F`：公开事实；
- `C`：客户确认；
- `B`：银行核验；
- `H`：工作假设；
- `P`：待审批；
- `A`：已批准。

这一设计解决两个常见问题：一是客户经理把公开报道、内部判断或AI推断写成客户事实；二是把“可考虑的方案”写成“银行已经承诺的方案”。状态标签同时约束对客版的内容边界。

### 2.5 建议书必须实行“内部工作版＋对客版”双版本

内部工作版可以包含：

- 未核验假设；
- 内部评级或风险判断；
- 产品适配意见；
- 额度、价格、条件的内部测算；
- 审批状态和分歧；
- 专家内部意见。

对客版只能保留客户可见、经核验或经批准的内容。两版必须分别编号和留痕，不能直接复制敏感内部判断，也不能把待审批事项写成确定承诺。

### 2.6 建议书应通过五道业务闸门流转

完整工作流实际包含G0—G5六个状态节点，其中G0是准备闸门，G1—G5是从客户核验到实施复盘的五个后续闸门：

| 闸门 | 核心要求 | 未通过时禁止事项 |
|---|---|---|
| G0 证据准备 | 公开信息有来源和日期；事实与假设分列；完成缺口清单 | 不得把假设作为确定事实带入正式建议 |
| G1 客户核验 | 目标、事件、痛点、决策人、期限经确认或标记待确认 | 不得直接进入正式方案承诺 |
| G2 专家设计 | 需求—方案—产品映射完整；主备方案、条件和风险明确 | 不得以客户经理个人判断替代专业评估 |
| G3 内部审批 | 产品、授信、价格、合规、合同、数据使用按权限批准 | 不得对客承诺额度、价格、收益和时效 |
| G4 对客确认 | 客户理解价值、条件、责任和下一步 | 不得将“客户已收到”视为“客户已接受并实施” |
| G5 实施复盘 | 里程碑、KPI、证据、问题和复盘闭环 | 不得把建议书交付视为经营任务完成 |

### 2.7 需求排序应量化，但不能机械替代专业判断

模板采用：

> 优先分 = 紧迫度（1—5）× 经营影响（1—5）× 战略匹配（1—5）

这一分数用于排序和讨论，不是自动决策规则。客户经理和专家仍需结合监管政策、客户承受能力、资源约束、风险条件、方案依赖关系及关键事件窗口进行专业判断。

### 2.8 方案设计应遵循“需求—根因—方案—产品—条件—价值—行动”链条

每项P1需求至少形成一张服务设计卡，包含：

1. 经核验的需求及客户原话；
2. 目标与量化基线；
3. 根因及影响链；
4. 服务设计；
5. 主方案；
6. 备选方案；
7. 银行产品或能力；
8. 非金融服务；
9. 客户收益；
10. 银行收益；
11. 前置条件；
12. 风险与控制；
13. 适用条件；
14. 双方下一步行动。

这条链能够防止三种失真：需求尚未核验就配产品；只写产品功能而不写客户价值；只写理想方案而不写条件、风险和责任。

### 2.9 产品组合不是产品并列，而是围绕客户任务分层成包

模板将服务组合分为三层：

| 层级 | 定位 | 典型内容 |
|---|---|---|
| 基础包 | 先解决高频、基础、可快速落地的问题 | 账户、结算、支付、代发、基础融资、基础线上服务 |
| 增强包 | 围绕价值链和现金流提升效率 | 现金管理、供应链金融、跨境结算与融资、票据、资金归集、数字化连接 |
| 战略包 | 支持重大经营事件和资本运作 | 并购、债券、股权、重组、上市、司库、出海、绿色转型、综合顾问服务 |

三层组合必须写明依赖关系、实施顺序和退出条件，避免把产品目录包装成“综合方案”。

### 2.10 专家协同必须任务化

专家参与不是把多人姓名放入建议书，而是形成明确协同单，至少包括：

- 客户ID、需求ID和方案ID；
- 协同主题；
- 需要的专业类型；
- 发起原因和明确问题；
- 必需输入材料；
- 期望交付物；
- 牵头专家和参与专家；
- 风险、合规、数据使用和审批事项；
- 截止日期；
- 对客口径；
- 完成状态和验收人。

专家输出必须回填到需求—方案—产品映射和实施计划中，不能成为独立、不可追踪的邮件或口头意见。

### 2.11 对客表达必须控制承诺边界

建议书中所有额度、价格、收益、时效、授信、合同和审批结果都必须附带适用条件。标准表述为：

> 本建议书所列产品、额度、价格、收益和时效均以适用条件、进一步评估及银行最终审批/合同为准。

建议书不替代授信调查、风险审查、合同、产品说明书或监管要求；客户经理及专家不得通过口头或书面材料越权承诺。

### 2.12 建议书必须落到30/90/180天实施管理

实施计划不是按时间简单罗列任务，而要同时记录：

- 阶段；
- 行动ID；
- 关联需求ID、方案ID；
- 任务；
- 责任方；
- 协同方；
- 计划开始和结束日期；
- 里程碑；
- KPI和目标值；
- 状态；
- 完成百分比；
- 依赖；
- 风险/问题；
- 应对措施；
- 实际完成日期；
- 验收证据；
- 复盘结论/后续动作。

阶段建议为：

- 0—30天：确认事实、完成必要材料和快速落地事项；
- 31—90天：完成核心产品和流程实施；
- 91—180天：扩大服务覆盖、验证经营价值、处理遗留问题并形成下一轮经营机会。

## 3. “写作模块”设计

用户要求将模板转换为写作模块。本会话形成的模块化写作逻辑如下。

### 3.1 模块一：拜访前经营假设

**输入：** 公开信息、银行内部授权信息、历史合作信息、行业资料。  
**处理：** 区分公开事实、银行核验事实、工作假设和未知项；形成三张图和访谈问题。  
**输出：** 拜访任务卡、客户快照、图谱、行业与价值链假设、提纲、风险预案。  
**禁止：** 将媒体信息、模型推断或客户经理经验直接写成客户确认事实。

### 3.2 模块二：首次拜访纪要与核验

**输入：** 现场或远程访谈内容、客户提供材料、会议参与人和约定事项。  
**处理：** 将客户陈述与证据逐项记录，标记状态，识别目标、触发事件、痛点、根因、影响、决策链和材料缺口。  
**输出：** 会议结论、核验记录、需求优先级、决策链、材料清单和下一步。  
**时限：** 拜访后24小时内完成。  
**禁止：** 用概括性“客户有融资需求”代替具体业务背景、用途、时间、金额、偿还来源和决策机制。

### 3.3 模块三：执行摘要

**写作公式：**

> 交流依据＋经核验的客户目标/事件＋银行对关键问题的理解＋三项以内服务主线＋分阶段推进方式＋审批与适用条件声明。

**要求：** 一页以内，让客户高层能够快速判断银行是否真正理解其业务。  
**禁止：** 直接用产品名称开篇；把客户尚未确认的判断写成结论；写入未经批准的额度和价格。

### 3.4 模块四：客户与行业诊断

**客户诊断结构：** 经核验事实 → 经营含义 → 机会/风险 → 证据来源。  
**行业诊断结构：** 行业阶段 → 政策与市场 → 价值链和账期 → 利润池 → 技术/绿色/跨境趋势 → 客户定位 → 银行服务启示。  
**要求：** 只保留与客户目标和方案选择直接相关的行业判断。  
**禁止：** 堆砌宏观数据；将行业平均判断直接套用于客户；没有时点和来源。

### 3.5 模块五：需求—方案—产品总览

**写作公式：**

> 需求ID＋客户目标/问题＋优先级＋服务主线＋方案ID＋产品/能力＋价值指标＋状态。

**要求：** 客户一眼看见“为什么做、做什么、带来什么、当前到哪一步”。  
**禁止：** 一个需求对应无序产品清单；产品与根因、目标、KPI之间无关系。

### 3.6 模块六：总体服务蓝图

**写作结构：** 当前问题 → 目标状态 → 服务支柱 → 关键举措 → 银行/客户责任 → 阶段 → 依赖。  
**要求：** 最多聚焦三条服务主线；体现融资、结算、现金管理、供应链、跨境、投行和非金融服务之间的关系。  
**禁止：** 每个专业条线各写一段、缺少统一主线和先后顺序。

### 3.7 模块七：分项服务设计卡

**写作结构：** 需求原话 → 量化目标 → 根因 → 服务设计 → 主方案 → 备选方案 → 产品/能力 → 非金融服务 → 客户价值 → 银行价值 → 前置条件 → 风险控制 → 适用条件 → 下一步。  
**要求：** 每个P1需求复制一张；需求、方案、产品和实施行动使用统一ID。  
**禁止：** 只有主方案没有备选；只有收益没有条件；只有银行动作没有客户动作。

### 3.8 模块八：组合包

**写作结构：** 基础包、增强包、战略包＋每层服务目的＋纳入产品和服务＋启动条件＋依赖关系＋退出/升级条件。  
**要求：** 根据客户成熟度、事件窗口和内部资源选择组合，不要求三包全部采用。  
**禁止：** 为体现“综合性”而强行塞入无关产品。

### 3.9 模块九：价值测算

**价值维度：** 资金成本、资金占用、操作效率、风险损失、收入增长、客户体验、管理透明度。  
**字段：** 基线、目标、计算口径、数据来源、假设、责任人、验证周期。  
**要求：** 结果区分确定值、区间值和假设值。  
**禁止：** 无计算口径的收益承诺；用银行收益替代客户价值；忽略实施成本。

### 3.10 模块十：实施计划与复盘

**写作结构：** 30/90/180天阶段目标＋行动＋责任人＋日期＋里程碑＋KPI＋依赖＋风险＋证据＋复盘。  
**要求：** 每项行动必须可验收；完成状态必须有证据。  
**禁止：** 使用“持续跟进”“加强沟通”等不可验收表述作为主要行动。

## 4. 数据对象与ID联动规则

五张表不是五个独立附件，而是围绕统一对象链联动：

```text
客户ID
  ├─ 客户事实/关系/业务/材料
  ├─ 行业判断与待验证假设
  └─ 需求ID
       └─ 方案ID
            ├─ 产品/能力ID
            ├─ 专家协同ID
            └─ 行动ID（30/90/180天）
```

建议采用如下编码：

| 对象 | 示例 | 说明 |
|---|---|---|
| 客户 | C-001 | 一户一号，集团客户可增加集团与成员层级 |
| 需求 | N-001 | 每项可核验客户需求唯一编号 |
| 方案 | S-001 | 主方案和备选方案分别编号 |
| 映射 | M-001 | 需求—方案—产品映射记录编号 |
| 专家协同 | EX-001 | 每项专家任务唯一编号 |
| 行动 | A-001 | 每项实施行动唯一编号 |

统一ID使访谈、方案、审批、实施和复盘能够追踪，后续也可直接转为知识工程中的实体、关系、状态和事件对象。

## 7. 后续承接建议

### 7.1 第一优先级：补齐同业研究证据包

建议按“大行—股份制银行—优质城商行”建立检索台账，至少记录：

- 银行名称；
- 材料名称；
- 来源网址或文件；
- 发布机构和发布日期；
- 材料类型；
- 可复用结构或字段；
- 适用客户与行业；
- 是否公开、是否仍有效；
- 证据等级；
- 对当前模板的影响；
- 采纳、调整或不采纳结论。

外部材料只能作为参考或证据候选，不能自动覆盖本行制度、产品和权限。

### 7.2 第二优先级：完成银行本地化

需要由目标银行补齐：

1. 本行客户分层和生命周期口径；
2. 产品目录、产品能力、适用条件、定价和审批状态；
3. 授信、风险、合规、法务、消保、数据使用和保密规则；
4. 客户经理、产品经理、专家团队和审批部门RACI；
5. 客户信息采集的最小必要字段和敏感信息边界；
6. 对客材料模板、品牌规范、免责声明和签批流程；
7. 行业模板、指标库、数据源和更新周期；
8. KPI计算规则、实施验收证据和复盘机制。

### 7.3 第三优先级：建立行业子模板

建议在通用母版之下，优先形成制造业、批发零售、建筑与基建、科技、医药、能源、跨境贸易、园区与集团客户等行业/客群子模板。每个子模板重点补充：

- 价值链；
- 行业关键事件；
- 现金转换周期；
- 核心经营指标；
- 常见痛点和根因；
- 典型产品组合；
- 风险红旗；
- 客户访谈问题；
- 数据来源；
- 适用和禁用条件。

### 7.4 第四优先级：转为知识工程和岗位智能体能力

当前模板可进一步拆为：

- 客户、集团、关系人、事件、目标、痛点、需求、方案、产品、条件、风险、行动、证据等本体对象；
- 访前准备、行业分析、访谈提纲生成、事实核验、需求识别、方案映射、专家协同、建议书写作、合规检查、计划跟踪等Skill；
- 客户经理主智能体＋行业/产品/风险/合规专家智能体协同；
- 人工确认、受控写回、版本管理和证据链。

但必须保持：AI辅助识别和写作，不继承授信审批、价格审批、合规判断、合同承诺或客户最终决策责任。

### 7.5 下一门禁建议

建议下一状态为：`READY_FOR_BANK_BUSINESS_REVIEW`，而不是正式基线或冻结。评审参与人至少包括：

- 对公客户经理代表；
- 分支行经营管理负责人；
- 行业研究或公司金融专家；
- 交易银行、授信、投行、跨境等产品经理；
- 风险、合规、法务、数据安全人员；
- 产品或知识工程负责人。

通过业务评审后，再进入本行产品和制度本地化；通过独立QA和Owner批准后，才可标记为本行正式标准。当前明确：`OWNER_APPROVAL_NOT_EXECUTED`，`FROZEN=NO`。
