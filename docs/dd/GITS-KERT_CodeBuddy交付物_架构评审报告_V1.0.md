## 3. 发现项与整改要求

### F01｜BLOCKER｜总契约身份与引用体系未对齐

**性质：已确认文本差异；是否存在获准改版仍待证明。**

证据：B §1–§11 将“§0.3 十层”“§2.2 17 服务端点”“§2.4 12 类事件”“§11.1–11.9”作为总契约验收锚点。A 实际采用总述 §1–§7 与 C01–C08，不存在这些对应章节；A §7 也明确 OWL、SPARQL 等不是首期必选。

影响：可能在按另一个同名版本或历史工程模板验收。若直接签字，会把工程扩展误当本次契约要求，或遗漏本次新增核心要求。

整改：提交 B 所引用总契约全文及 hash；与 A 做章节、需求、约束逐项 diff。存在批准变更的，附 ADR/CR 与批准依据；不存在的，修正引用。十层可以保留为交付目录，但必须映射 C01–C08，不能替代需求结构。

关闭证据：唯一参考版本记录、差异说明、批准状态、无悬空锚点的追踪表。责任：Tech Lead、契约 Owner。

### F03｜MAJOR｜系统权威与迁移合同未落实到清单

**性质：覆盖缺口，不认定实际系统已经重复存储真相。**

依据：A C01、C08 CR-01/02；B §4、§6、§12。

A 要求五个逻辑子系统、六个责任边界。B 聚焦“操作本体↔语义本体双核心”与 GITS 服务，未列公共核心独立、银行源事实、指标模块、KERT 知识发布和 GITS 经营状态的逐对象权威映射。

整改须交付“对象/字段—定义者—保管者—唯一写入口—执行者—投影消费者—版本与撤销”矩阵，至少覆盖客户身份、账户余额、产品主档、产品条款、MetricDefinition、MapVersion、ReviewDecision、Release、任务、业务决定、回执。区分 GITS 的人工经营决定与银行源系统的正式授信等业务决定。

双核心作为技术组织方式并非自动错误；必须说明如何满足公共核心独立与域内所有权。Java 工程和既有 OWL 等能力也不应无故删除；KERT Python Core 与 Java Skill Runtime 按适配关系映射，未经变更评审不以单一应用栈覆盖全部系统。

关闭证据：权威矩阵、写入口/API/表或文档记录的对应关系、CR-01/02 迁移与兼容证据。责任：语义、数据、KERT、GITS 各 Owner/TL。

### F04｜MAJOR｜知识地图与注册中心尚未形成可验收的运行合同

**性质：覆盖缺口。**

依据：A C02、C06；B §4 的 KnowledgeMap/KnowledgeElement/RoutePolicy 与 §12 的内存快照/Wiki 声明。

“有地图对象或 Wiki”不等于模型可以安全发现并激活分散知识。清单没有明确六类注册对象及它们的引用闭包，也没有将 discover → expand → plan → execute 与版本、权限、能力探针逐项对应。

整改至少覆盖：

1. AssetCatalog、SourceRegistry、CapabilityRegistry、QueryRegistry、MapRegistry、ReleaseRegistry 六个逻辑模块，可合并部署。
2. 内容知识图、任务知识地图、运行依赖图三种视图；内容关系不能直接成为工具调用权限。
3. 四类 assetClass 与 subjectCategory 分离；稳定 ID、不可变版本、用途/范围与外部定义引用。
4. MapSpec 到 Wiki、图投影和模型说明的单源生成；不能各自编辑一套权威内容。
5. 固定 TaskContext、release/core/catalog/route 版本和授权，生成 canonical planHash；跨语言有黄金字节样例。
6. 必需资产缺失、未注册能力、同优先级路由、越权目录/邻居/计数、缓存撤权都有拒绝或失效合同。

关闭证据：注册模型/API、任务地图样例、计划正负例与 T05–T07/T17 映射；申请实现验收时提供实际请求、输出、trace。责任：KERT TL。

### F05｜MAJOR｜自动建图到审核发布的主链没有独立验收

**性质：覆盖缺口。**

依据：A C03；B §4 的 Claim 调和、§3 的知识发布事件、§0 的 ControlledAction 人控。

这三类描述不能替代知识认定流水线。业务动作确认与知识地图发布是不同审批对象；Claim 调和也不能仅按评分确立银行权威。

整改：以一份带新旧版本、条件、否定和同名主体的文档走完整设计实例：SourceVersion → Fragment/EvidenceSpan → CandidateAssertion → 身份对齐 → CandidateMap → ReviewPackage → 内容认定与地图用途认定 → StagedRelease → 不可变 Release → 撤销/新版本。任务模板和能力合同不能仅从文档抽取得出。

强制验证：审批绑定准确内容 hash、版本、范围和用途；审批后改字必须失效；必需投影 ready 后通过 CAS 切换当前发布指针并记录 outbox；禁止半发布；撤销不能等异步缓存自然过期才生效；候选图不得通过普通检索混入正式结论。

关闭证据：状态机、审核界面/接口合同、Release manifest、发布/恢复/撤销正负例、T08–T10/T18–T21 追踪。真实审批在设计包阶段可待实施，但不能把模拟 reviewer 作为真实签署。责任：KERT TL、知识 Owner、任务地图业务 Owner。

### F06｜MAJOR｜分析语义服务覆盖不足，是最需要优先补齐的业务正确性风险

**性质：覆盖缺口。**

目前未见明确的 MetricDefinition、指标批准责任、受控 QueryPlan、账户日粒度、跨币种政策、快照复算及授权执行清单。本体建模与 SQL 文件存在，均不能证明日均存款算对。

必须补充：

| 合同对象 | 必须提供的具体证据 |
|---|---|
| 指标 | metricId/version、Owner/approvalRef、定义 hash、分子分母与舍入规则 |
| 数据映射 | accountId+businessDate+snapshotId 唯一性，账户当日归属、允许 join 路径与基数 |

关闭证据：C04 指标合同、计划/结果正负例、T11–T16；实现阶段提供独立算法复算与实际查询输出。责任：银行模拟平台 TL、指标 Owner。

### F08｜MAJOR｜种子与样例未证明覆盖完整模拟银行和非结构化知识闭环

依据：A C07；B §11 的 seeds、请求/响应/事件样例。
