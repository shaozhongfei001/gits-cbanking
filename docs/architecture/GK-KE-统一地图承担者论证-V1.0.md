# 论证：「统一地图 + 知识路由」的承担者 —— 本体 / 图谱·WIKI / 分工

> **编制**：Tech Lead｜**日期**：2026-09-14｜**状态**：**待 Owner 裁定（论证件，非结论）**
> **命题来源**：Owner 2026-09-14 —— 「*本体承担统一地图*是**探讨或愿景，不是定论**，恰好需要协助调研论证；
> 是否本体是最佳方案，还是**图谱/WIKI 作为地图**是一种候选」
> **本件不是**：ADR 采纳、合同变更、实现授权

## 0. 先把模糊命题拆成**可判定**的子问题

原命题"用本体模型承担结构化与非结构化知识统一地图、知识路由"混合了五件事。
不拆开就无法论证，只能各说各话。拆解如下：

| # | 子问题 | 判定方式 |
|---|---|---|
| **Q1 导航** | 「去哪找、加载什么、给多大预算」由谁承担 | 该层能否**指导执行**而非仅显示关系 |
| **Q2 语义** | 「对象是什么、关系含义、状态与边界」由谁承担 | 事实是否**确定性可校验** |
| **Q3 统一** | 结构化与非结构化知识如何"统一" | 是否存在**同一引用空间**，还是靠人肉对齐 |
| **Q4 路由** | 按任务择序由谁决策、依据什么 | 决策是否**可解释、可回放、fail-closed** |
| **Q5 一致性** | 谁改、谁负责、如何防止两份定义漂移 | 能否定位**唯一变更责任与源版本** |

> **关键前提（来自设计原文，不是我加的）**：
> - 《项目总契约》§5：**「知识地图是面向任务的资产/能力导航模型；实体关系图是内容表示。」**
> - 建议书 V2.0 §4.3：**本体层**规定对象身份与关系含义；**分析语义层**规定数值粒度/时间/币种/聚合；
>   **规则层**在明确前提下计算；**工作流层**决定谁确认、何时执行、失败如何恢复。
> - 建议书 V2.0 第 185 行：**「不能同时手工维护两份可独立修改的定义。」** ← **本论证的最强约束**
> - ADR-0015：**「Knowledge Map 控制发现与路由；本体负责对象、关系、状态和约束」**（状态 = `Proposed`）

## 1. 三个候选方案

| 候选 | 主张 | 承担者分工 |
|---|---|---|
| **A 本体中心** | 本体同时承担**导航 + 语义 + 路由**；地图是本体的一种视图 | 本体 = 全部 |
| **B 图谱/WIKI 地图中心** | 地图（Markdown/图谱）承担导航与发现；本体退化为可选增强 | 地图 = 导航（+部分语义），本体 = 可选 |
| **C 分工 + 投影** | 地图管导航、本体管语义、路由择序、**ActivationPlan 唯一汇合**、Wiki 仅只读投影 | 三者分工，单一汇合点 |

> **候选 C 就是仓库现有 ADR-0015 / 0016 / 0017 的提案内容**，三条状态均为
> `Proposed for P20 Owner review` —— **从未被 Owner 接受，也从未被任何实例验证**。

## 3. 逐准则论证

### 3.1 候选 A（本体中心）：**在 C4 上直接违规**

| 准则 | 判定 | 依据 |
|---|---|---|
| C1 | ✅ 理论上最强 | 本体可表达任意导航关系 |
| C4 | ❌ **违规** | 一旦"本体承担地图"，地图与本体即**同一物**；但现实是**地图已在 Markdown/git 中被人编辑**（`specs/knowledge-architecture/maps/**`），要求人用 Turtle 写导航 = 逼出第二份定义 |
| C5 | ⚠️ 未解决 | 非结构化抽取产物（`l11` 的 29 EvidenceSpan / 14 FieldAssertion）若要进本体，需先有**实体归一**，而归一规则本身要被治理 |
| C7 | ✅ 强 | 本体天然带版本与身份 |
| C8 | ❌ 最贵 | 总契约 §7 明写首期**不要求 OWL 推理/SPARQL**；让本体承担导航必然引入推理与查询 |

**A 的致命处**：设计原文 §5 **已经否掉了它** —— 「知识地图是**面向任务的资产/能力导航模型**；**实体关系图是内容表示**」。
把两者合并，等于取消这句区分，也就取消了"任务级导航"这一独立治理对象。

### 3.2 候选 B（地图/WIKI 中心）：**只赢一半，且在 C3 上失守**

| 准则 | 判定 | 依据（**本仓实测**） |
|---|---|---|
| C1 | ✅ **已跑通** | 地图已是 Markdown + front matter（`mapType`/`entrypoints`/`assetRefs`/`skillRefs`/`routePolicyRef`/`maxInitialTokens`），且 `KnowledgeWikiPort.renderMap()` 把它渲染成 LLM 可读 Markdown；P22/P23 已交付"知识地图驱动访前报告（按 7 个 KI 分组）"，**这是真实产品行为** |
| C2 | ⚠️ 弱 | 地图只能给"加载什么"，给不出"**事实是否成立**" |
| C3 | ❌ 失守 | `MAP_FIRST` 若用于事实类任务会退化为文档 RAG —— ADR-0015 的 Positive 明确写着「**避免所有场景都退化为文档RAG**」；而 `RP-CORP-RM-001` 已把 `FACT_RECONCILIATION_30M` 定为 `ONTOLOGY_FIRST`，理由原文是"对象、关系、数值和规则边界**必须确定性校验**" |
| C5 | ✅ 强 | 非结构化材料天然适合 Wiki 承载 |
| C7 | ⚠️ 弱 | Markdown 正文**无字段级版本与变更责任**；只能靠 front matter |

**B 的致命处**：本仓已实测到该形态；而 `RP-CORP-RM-001` 四条路由规则本身就说明**设计不打算让地图包打天下**。

### 3.3 候选 C（分工 + 投影）：**准则上最均衡，但有一个未解决的硬风险**

| 准则 | 判定 | 说明 |
|---|---|---|
| C1 | ✅ | 地图管导航（已跑通）；本体管事实 |
| C2 | ✅ | Route Policy 产出唯一 route（`DefaultRoutePolicyEvaluator` 已实现，含歧义 fail-closed） |
| C3 | ✅ | `DefaultActivationPlanner` 已实现 fail-closed：权限未决 / production 模式 / route 与合同不一致 / 资产未登记 → 一律拒绝 |
| **C4** | ❌ **未解决 ← 唯一硬风险** | 地图（`specs/.../maps/*.md`）、本体（`specs/semantic/gits-core.owl.ttl`）、Wiki 投影**三处各自可独立修改**，正是建议书第 185 行禁止的"两份（此处是三份）可独立修改的定义" |
| C5 | ⚠️ | 有抽取（`l11_extract_evidence_spans.py`），但产物是 JSON 断言，**未进本体** |
| C6 | ⚠️ | 产品卡的 `prerequisite_product_ids`/`mutex_product_ids`/`complementary_products`/`admission_criteria` **已是结构化 YAML**，但**未进本体、也未被产品消费** |
| C7 | ✅ | `ActivationPlan` 含 `versions{knowledgeMap,routePolicy,activationContract,ontology}` + `planHash` + `plannerVersion` |
| C8 | ✅ | 与 §7 一致：不引入 OWL 推理要求 |

**C 成立的充要条件**（这是本论证的核心主张）：

> **C 只有在补上"单一权威 + 投影 + ID 锚定"这三条硬约束后才成立**，否则它比 A/B 更糟
> —— 因为它把不一致的风险从"两个方案之争"变成"三处表示之间的静默漂移"。

具体三条：
1. **本体是实体/关系/状态的唯一权威**（地图不得定义实体语义）；
2. **地图是任务导航的唯一权威**，其 `assetRefs` / `domainRefs` / `skillRefs` **必须锚定本体个体 ID**，
   引用不存在的个体 ⇒ **规划必须 fail-closed 拒绝**（而非静默忽略）；
3. **Wiki / OpenWiki 是只读投影，可重建**（ADR-0017 已定边界），**不是权威源**。

## 4. 结论

| 候选 | 结论 |
|---|---|
| **A 本体承担统一地图** | ❌ **不成立**。与设计原文（总契约 §5）冲突：地图是**导航模型**，实体关系图是**内容表示**。合并二者 = 取消任务级导航这一独立治理对象，并把最贵的推理引入首期（违反 §7） |
| **B 图谱/WIKI 作为地图** | ⚠️ **只是候选的一半**。它在"导航与发现"上已被本仓跑通且成本最低；但**不能承担事实确定性与规则约束**，用作事实任务会退化为文档 RAG（设计明确反对） |
| **C 分工 + 投影** | ✅ **推荐**，但**必须补 §3.3 的三条硬约束**。它就是 ADR-0015/0016/0017 的方向 —— 而这三条**至今仍是 `Proposed`，从未被实例验证** |

**一句话**：**"统一"不发生在某一个表示里，而发生在"路由 + 计划"这一汇合点上**；
本体负责"是什么"，地图负责"去哪找"，Wiki 负责"给人看"，**ActivationPlan 负责把它们合起来并被校验**。

**外部实践与理论依据一致**（仅作技术判断，不覆盖业务口径）：
OWL 开放世界语义意味着"未记录 ≠ 为假"，SHACL 只校验图是否满足约束，**都不证明断言客观真实**
（建议书 §4.3 已引 W3C OWL 2 Primer / SHACL）；工业界的共识同样是
**本体定"应如何组织"，知识图谱承载"实例与关系"，二者是定义与实例的关系而非替代关系**
（检索所得多源均持此界分）。这与候选 C 的分工一致，与候选 A 的"合并"相反。

## 5. 可证伪的验证实验（**与 Owner 已批准的 1+2 最小切片绑定**）

论证到此仍是纸面。**下面三个反例是判据：其中一个失败，候选 C 即不成立，须回到 A 或 B。**

| # | 实验 | 通过判据 |
|---|---|---|
| **V1** | 一个任务（`PRE_VISIT_PREPARATION`，路由 `ONTOLOGY_THEN_MAP`）跑通完整链：路由裁决 → 本体查实体/关系 → 地图按结果定向激活资产 → SKILL 调用 → 输出证据 | 有**可复核的原始输出**（含 `planHash`、`versions.ontology`、路由理由） |
| **V2** | **反例1**：只改本体（如给客户加一条互斥关系），**不动地图** | 计划**必须变化**。若不变 ⇒ 本体未被消费 ⇒ **A 不成立且 C 未落地** |
| **V3** | **反例2**：地图引用一个**本体中不存在**的个体 | 规划**必须拒绝（fail-closed）**。若静默放行 ⇒ "ID 锚定"形同虚设 ⇒ **C 的硬约束 2 未落地** |
| **V4** | **反例3**：把同一对象在地图与本体中**手工改成不一致** | 门禁**必须检出**。若检不出 ⇒ C4 无法保证 ⇒ **C 比 A/B 更危险** |

> **纪律**：V2–V4 若"通过"是因为**夹具缺失导致断言空转**，则视为**未验证**（本仓已有前例：
> 6 个 Loop 首报全绿实为断言空转）。每个反例都必须附**变异前后对照**。
