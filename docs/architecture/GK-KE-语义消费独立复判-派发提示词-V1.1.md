## 附二：V1.1 发出后的**补充披露**（2026-09-13，委托方自曝，必须读）

> **披露义务**：委托方在发出本提示词后继续攻击自身链路，发现一项**与本轮判定材料直接相关**的事实。
> 按纪律「明知有疑点不得沉默」，特此补充。**此披露不放宽也不收紧 §五 的任何判定纪律。**

**事实（可复现，命令见下）**：本轮权威观测中下游的 `coverageStatus = "PARTIAL"`，
**在当前实现下不是"依上游状态映射"的结果，而是"上游状态未送达"时的默认分支取值。**

- 下游技能自身契约（`bank-front-kyc-gap-check/references/input-schema.md`）要求字段名
  **`upstreamStatus`**，并明文「不得改写」；
- 而 GK 映射合同产出的下游输入里**没有** `upstreamStatus`，只有 `status`
  （上游 `executionStatus` → 叶名 `status`）；
- 该技能的确定性仿真实现读的是 `upstreamStatus` ⇒ 取不到 ⇒ 落
  `status_map.get(None, "PARTIAL")` 默认值。
- **实测**：走真实映射把上游状态改为 `NOT_RUN` / `SUCCESS` / `FAILED`，
  下游 `coverageStatus` **恒为 `PARTIAL`**，输出**逐字节相同**；
  而按技能契约键名直传 `upstreamStatus=NOT_RUN` → 正确得 `NOT_RUN`。

**对你（执行者）的含义**：

1. 观测中的 `coverageStatus="PARTIAL"` **不构成"下游消费了上游状态"的证据**；
   它只说明"上游状态未送达，故取默认"。
2. 因而判据 **`S3`（`NOT_RUN ≠ 没有`）在本轮材料下仍可能无法判定** ——
   若你得此结论，**这是正确结论**，不是你的失误。
3. **不要**据此推断"上游状态被消费"或"未被消费"中的任一方；
   你能判定的是**材料自身**显示了什么。
4. 该事实的根因与完整攻击记录：`loops/GK16-trust-hardening/FAILURES.md` 的 **T-28 / T-30**
   （含命令与原始输出）。
