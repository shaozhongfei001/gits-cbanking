## 1. U-1｜根域名 / 根 IRI 前缀（我方为输入方，不给结论）

### 1.1 候选类别（≥3，中性表述）

| 代号 | 类别 | 说明 |
|---|---|---|
| **候选域-A** | 企业自有域下的新子域 | 使用机构已持有并自主续期的域名，新增语义专用子域 |
| **候选域-B** | 组织级中立持久域（独立于当前系统/仓库） | 由机构控制、但语义上**不绑定任何现有系统或产品线**的域名，通常由架构治理方持有 |
| **候选域-C** | 受控离线命名空间 | 非 HTTP 解析路径（如受控 URN 空间或内容寻址）；与 U-2 路线 B 配套 |
| **候选域-D** | 社区/联盟类持久标识域 | 由第三方治理机构维护的持久标识域（机构控制力弱于 A/B） |

### 1.2 对比维度（我方建议的评估口径）

| 维度 | 说明 | 为什么对本项目关键 |
|---|---|---|
| 持久性 | 域名续期责任、历史沿用时长、被弃用风险 | 公共术语 IRI 一旦发布即难以回收；「持久」是本 ADR 的核心动因 |
| 控制权 | 谁持有、谁能改解析、谁能单方废止 | 须与设计 §2.2「任一单域都无充分权力单独改变其语义」一致；防止公共层被单系统私有化（`R-PRIV`） |
| 解析能力 | 能否做 `303 + Accept: text/turtle` | 影响 U-2 路线 A 可行性；不能解析则须走内容寻址 |
| OPEX | 证书、托管、运维、合规审计成本 | 公共层长期运行成本须可预期 |
| 迁移影响面 | 现有消费方（含 KERT 硬编码、`planHash` 派生链）改写量 | 由 WI-A2 处置表量化（`CONTROL_PLANE_REQUIRED` 14 项为真实修码项） |
| 外部可引用性 | 合作方/监管方能否稳定引用 | 影响中立的**可信度**：外部引用方更信任「不隶属单一系统的域」 |
| 对外暴露风险 | 域名/路径是否泄露内部结构或客户信息 | 公共 IRI **必须**不含机构内部层级、业务线代号、客户信息 |
| 与 D3 权责匹配 | 决策权是否落在「语义架构 Owner + 域名 Owner」两人手中 | 若落在第三者，D3 决议将无法覆盖 |

### 1.3 我的**建议**（非结论）

1. 评估集合建议收敛为 **候选域-A / 候选域-B / 候选域-C** 三类：候选域-D 因「控制权」与「与 D3 权责匹配」两项天然不利，仅在与外部生态强绑定时才值得展开（若选，须额外证明其治理可持续性）。
2. 无论选哪一类，**必须在 ADR 正文写明以下三件事**（否则我方在 §0 前置条件之外无法评估长期风险）：
   - ① **续期与所有权责任人**（具名角色，不是团队名）；
   - ② **变更解析目标的前置条件**（谁批准、是否需双侧 Owner 会签）；
   - ③ **弃用/失效时的处置预案**（IRI 失效是否允许；若不允许，如何做长期托管）。
3. IRI 形态建议沿用 ADR §4 的四段式（`{NS-L1}`/`{NS-L2}`/`{NS-L3}`/`{NS-L4}`）与大小写/保留段约束；**本项与根域选择解耦**，可先行确认（属我的联签范围，我可以先签这一半）。

## 2. U-3｜LEGACY 双发布窗口长度（我方为决策 Owner，仍只给选项与建议）

### 2.1 先决问题：「发布周期」到底指谁的周期？

这是 U-3 最容易被误签的地方，须先定义清楚：

| 可能定义 | 问题 |
|---|---|
| 以 **KERT 的发布周期** 计 | ① KERT 无公开固定周期 ⇒ 不可测；② **与 Wave 1 条件 ⑤「不随 KERT 发布节奏变更」直接冲突**（窗口长度会随 KERT 节奏漂移）⇒ **不建议采用** |
| 以 **独立语义契约库的发布周期** 计 | 与 Wave 1 独立版本线一致，可测（每次 L1 库发布为一个周期）；**建议采用** |
| 以 **日历时长** 计 | 可测，但与时序风险脱钩（窗口内若零发布，等价于无限期拖延） |
| 以 **消费方切换完成度** 计（门控） | 可测且与真实风险对齐（切换完成才算窗口结束） |

### 2.2 候选方案

| 代号 | 方案 | 时长/条件 | 优点 | 风险 |
|---|---|---|---|---|
| **窗-A** | 固定短窗 | 1 个契约库发布周期 | 简单、快 | 消费方未切完（WI-A2 处置表未清）就到期 ⇒ 被迫二选一：延期（形同虚设）或强行退役（破坏消费方） |
| **窗-B** | 固定日历窗 | 3 个月 | 可测、便于对外沟通 | 与迁移实际完成度脱钩 |
| **窗-C** | 固定日历窗（长） | 6 个月 | 给硬编码清理留足时间 | 双发布期过长 ⇒ 两套 IRI 长期并存，噪声与误用风险上升 |
| **窗-D** | **门控式（Gated）** | 唯一充分条件 = **退役门四条全满足**；并设**最小期限**（不短于 1 个契约库发布周期 + ≥1 完整验证周期） | 与真实风险对齐；不会「到期即退役」；也不需要无限延期 | 需要在报告中显式记录「门未达」的持续状态（多一条台账负担） |
| **窗-E** | 门控 + 硬上限 | 同窗-D，另设不可逾越的上限（如 12 个月），逾期须 Owner 决议延期 | 防「门控式无限期」 | 上限到期若未满足门，仍需 Owner 裁定（回到人治） |

### 2.3 我的**建议**（非结论）

1. **建议采用「门控 + 最小期限」形态（窗-D 为主，与窗-E 的硬上限优点合并）**，理由：
   - ADR §5.2 已把退役门定义为**四条判据**（处置表 100% 关闭或具名豁免 / 碰撞检查绿 / import closure 单版本 / 双侧 Owner 签署退役记录）。若同时用固定日历时长，实际会得到「两个充分条件」，二者冲突时无法判定 ⇒ 反而制造解释空间；
   - 执行计划 §6 已规定「旧值只读 ≥1 验证周期」，窗口只需保证**不短于**该下限；
   - 条件 ⑤（不随 KERT 节奏变更）要求窗口的计量单位**不能**是 KERT 的发布节奏。
2. **建议 U-3 的签署内容拆成三小项**，避免把可执行参数与原则混在一句话里：

| 小项 | 内容（建议形态） |
|---|---|
| U-3.1 | 计量单位：**契约库发布周期**（非 KERT 发布周期） |
| U-3.2 | 最小期限：≥ 1 个契约库发布周期 **且** ≥ 1 个完整验证周期（两者取长） |
| U-3.3 | 关闭条件：**退役门四条全满足**为唯一充分条件；另设硬上限，逾期由 Owner 决议（是否设上限请 D3 双 Owner 表态） |
3. 建议在 ADR 中**显式记录**「窗口内 KERT 发布节奏变化不影响 U-3 计时」——这是条件 ⑤ 的落地证据，未来独立 QA 可据此核验。

## 3. U-4｜`authorityEntity` / `hostingRepo` 具体值（我方 + 契约库 Owner 为决策 Owner）

### 3.1 为什么这两个字段必须分开（本项是 U-4 的实质，而非措辞）

设计 V2.0 变更 #16 要求用双字段替代原 `authorityRepo`。理由：**「谁对术语定义负责」与「制品物理放在哪」是两件事**；混同会直接导致委员会议题「公共模块被 KERT 事实私有化」复发（`R-PRIV`）。因此：

- `authorityEntity` 变化 ⇒ 治理主体变更，属**重大治理事件**（须公告、须重签发布权限）；
- `hostingRepo` 变化 ⇒ 搬家，**不改变**权威主体与版本线，只需工程核验（重钉 + 解析测试）。

**判定建议**：门禁强制「两字段非同一值」，且 `hostingRepo` 变更**不得**触发 `authorityEntity` 自动变更（`ONTOLOGY_PROVENANCE_FIELD_CONFLATED`，见 `ONTO1-L1-建模规则R1-R9修订版-DRAFT.md` R8）。

### 3.2 `authorityEntity` 候选

| 代号 | 载体形态 | 说明 | 评估 |
|---|---|---|---|
| **实体-A** | 虚拟治理实体（具名） | 例：以「公共语义治理实体」为名，具名到责任人（公共语义 Owner），实体不隶属任何系统 | 与设计 §2.2 条件 2（单域无权独改）最契合；**建议优先** |
| **实体-B** | 现有委员会/架构治理组织 | 复用已有架构委员会作为实体 | 治理可持续性强；但须确认其是否愿意承担**出版级**责任（版本、弃用期、退役记录签署），而非仅评审 |
| **实体-C** | 某一具体系统/团队/仓库名 | 直接用某系统或团队作为权威实体 | **不建议**：与「防单系统私有化」直接冲突；未来系统改名即污染全部 `PROVENANCE.json` |
| **实体-D** | 外部机构/合作方 | 由外部方作为权威实体 | **不建议**（试点期）：治理权外移，退出成本高 |

**建议**：`authorityEntity` 取 **实体-A**，并在 ADR/库 `README` 中写明「该实体为治理实体，其物理寄放见 `hostingRepo`」；若选实体-B，须同时明确**出版职责**（谁签版本、谁批退役）落在具名角色而非组织名。

### 3.3 `hostingRepo` 候选

| 代号 | 形态 | 说明 | 评估 |
|---|---|---|---|
| **库-A** | **独立受保护语义契约库** | 独立 Owner / 版本线 / 访问控制 / 发布流水线 | 与裁定 3、Wave 1 五条件完全一致；**建议唯一候选** |
| **库-B** | 主仓（GITS 或 KERT）子目录暂寄 | 在既有仓内开目录 | 迁移期可用（Wave 1 之前），但**不得**作为 `hostingRepo` 的长期值；会被追认为私有化 |
| **库-C** | 第三方托管平台仓库 | 外部平台承载 | 需先过安全与合规（凭据、审计），本轮不建议作为长期值 |

**建议**：`hostingRepo` 取 **库-A**；在库未建成前（Wave 1 未开工），`hostingRepo` 字段填**具名未定点**（如 `PENDING(WAVE1)`）而**不得**填暂寄路径 —— 理由：一旦填了暂寄路径并发布制品，后续换库会产生一次 `PROVENANCE.json` 全量变更，正是我们要避免的噪声。

### 3.4 U-4 的签署内容建议（拆项，便于分步签）

| 小项 | 内容 |
|---|---|
| U-4.1 | 双字段语义定义（权威主体 vs 物理寄放）+ 「不得混同」判定 |
| U-4.2 | `authorityEntity` 取值（建议实体-A，见 §3.2） |
| U-4.3 | `hostingRepo` 取值（建议库-A；不可用前的具名占位形式 `PENDING(WAVE1)`） |
| U-4.4 | 变更审批规则：`authorityEntity` 变更须 Owner 批准 + 公告；`hostingRepo` 变更须重钉 + 解析测试绿 |

## 4. 我不建议的选项（anti-recommendations，供反向校验）

| # | 不建议 | 理由 |
|---|---|---|
| N-1 | 把任何占位值（`bank.example` 等）作为「临时正式值」先发布、后替换 | 一经发布即可能被外部引用/缓存；ADR 已禁；替换成本高于等待 |
| N-2 | 用「KERT 发布周期」定义 U-3 窗口 | 与 Wave 1 条件 ⑤（不随 KERT 节奏变更）冲突，且不可测 |
| N-3 | 把「双发布窗口到期」作为退役的唯一充分条件（纯日历窗） | 与退役门四条冲突 ⇒ 出现两个充分条件，冲突时无判定规则 |
| N-4 | `authorityEntity` 填系统名/团队名/仓库名 | 单系统私有化风险复发；系统改名污染元数据 |
| N-5 | `hostingRepo` 长期填主仓子目录 | 同上，且会被留痕为「公共层寄放于某一方仓」 |
| N-6 | 在 D3 签署前先行发布 L1 IRI 以「解冻开发」 | 直接违反 `LOOP.yaml.gate_state.forbidden_now` 与 ADR §9；且会造成二次重钉 |
| N-7 | 重构项使用 `owl:equivalentClass` 做迁移桥接 | 语义已收窄/改变，等价声明会制造错误推理（04-D 硬约束） |
