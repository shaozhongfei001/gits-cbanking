## 1. 问题（**已实测，非推测**）

### 1.1 实测事实

| 事实 | 证据 |
|---|---|
| 下游输出**无**任何结构化覆盖/限制状态字段 | `bank-front-kyc-gap-check/references/output-schema.md` 顶层仅 `schemaVersion` / `skillId` / `customerId` / `generatedAt` / `kycGaps` / `warnings` |
| 下游"未执行"仅以**文字约定**表达 | `bank-front-kyc-gap-check/SKILL.md:48`「无触发源时：输出『无缺口』占位，不强行制造缺口」；`:140` 同 |
| **实测该文字约定会产生错误结论** | 2026-09-13 独立判定（`evidence/gk-ke-semantic-consumption/INDEPENDENT-JUDGEMENT-S1-S5-V1.0.md`）：上游 `reconciliationStatus=NOT_RUN`（未执行）时，下游 `warnings` **正确写出**了「规则覆盖不足……覆盖状态待核实」，**但结论字段 `kycGaps` 为空** —— 与"上游正常运行且无冲突"场景的输出**在结论层完全同形** |
| 独立判定据此判 **S3 = FAIL** | 同上，判定记录 §二 S3 |

### 1.2 为何这是合同问题，不是实现问题

> 下游**行为上做到了**它合同允许的最好结果：合同只给了 `kycGaps`（结论）与 `warnings`（自由文本），
> 它就只能在 `warnings` 里写覆盖不足，而 `warnings` **不是结论字段**。
>
> **"没查"与"没发现"在结论层不可区分 —— 这是合同的表达力缺口。**

### 1.3 一个已证伪的替代方案（供参考，**请勿采用**）

我们曾考虑"用 `warnings` 关键词判定"（关键词出现即算满足）。
**本次实测已证伪该方案**：同一份输出 `warnings` 写了"规则覆盖不足"，结论 `kycGaps` 却为空 ——
关键词启发式会**假通过**。故本请求要求的必须是**结构化受控字段**，不接受文本约定。

## 2. 请求项（**按优先级**）

### P0 · R1：下游输出顶层结构化**覆盖/限制状态**字段

| 项 | 内容 |
|---|---|
| **能力** | `bank-front-kyc-gap-check`（`SK-FRONT-006`） |
| **位置** | `references/output-schema.md` **顶层**（与 `kycGaps` 并列） |
| **建议字段名** | `coverageStatus`（或 `limitations[]`；命名由你方决定，我们只要求**结构化 + 受控枚举**） |
| **建议取值** | 至少区分：`SUCCESS`（触发源已完整评估）/ `NOT_RUN`（上游未执行，本能力无从判断）/ `PARTIAL`（触发源或规则覆盖不完整）/ `FAILED` |
| **是否必填** | **必填**（缺失即视为合同违规） |
| **为何 P0** | 这是 S3 判据**结构化路径的唯一前提**；不给该字段，S3 在合同层**永久不可判定** |
| **验收** | 同一客户、上游 `NOT_RUN` 与上游正常两种情况，下游该字段取值**必须不同** |

> **重要**：我们不要求你方改变业务结论（"不上报缺口"可以是正确行为）。
> 我们只要求**把"为什么没有缺口"表达为结构化字段** ——
> 「查过且没有」与「没查」在结论层必须可区分。

### P0 · R5：`conflicts[].ruleId` 禁止占位符

| 项 | 内容 |
|---|---|
| **能力** | `bank-front-fact-reconciliation`（`SK-FRONT-004`） |
| **现状（实测）** | 输出 `ruleId = "RUL-FRONT-001-xxx（逻辑矛盾/信号背离，具体子编号待映射）"` |
| **问题** | 占位符**不可作为追溯键**；下游即使引用了它，也无法被机器校验 |
| **请求** | `ruleId` 必须为**具体子编号**（如 `RUL-FRONT-001-003`）；无法映射时**置空或显式标记未映射**，不得以 `xxx` 占位 |
| **验收** | 输出中不出现含 `xxx` 的 `ruleId` |

### P1 · R2：`kycGaps[]` 元素增加 per-gap `status`

| 项 | 内容 |
|---|---|
| **能力** | `bank-front-kyc-gap-check`（`SK-FRONT-006`） |
| **位置** | `references/output-schema.md` 的 `kycGaps[]` 元素 |
| **建议取值** | 至少区分：`OPEN`（待核实）/ `CLOSED`（已核实并关闭）/ `PENDING` |
| **为何** | 使 S4（"假设不得关闭缺口"）可机器校验。现无该字段，只能靠"动作字段是否为空"作**代理指标**，证据力不足 |
