## 0. 一句话结论

- **现状**：产品知识**有 schema、有校验器、有 API**，但**没有 ProductCard 内容**。
  `SIM-ASSET-P001.json` 是**卡片集合的选择规则**（`SELECT_OR_CONSTRUCT`），**不是条款内容**。
- **首期只做 1 个产品的实质内容**（建议书 §15.1「一条专业访前链」，模式为**融资需求访前**）。
- **关键设计决策**：
  1. 条件判断**允许**输出"当前证据下 TRUE/FALSE/UNKNOWN"，**禁止**输出正式准入
  2. **体检未通过的产品不得进入可执行候选判断**（§8.1）
  3. **没有登记/证据就不能把"未见重复融资"判 TRUE**（§8.3）

## 2. ProductCard 设计（§8.1）

### 2.1 必填字段（13 项，§8.1 原文要求）

| # | 字段 | 说明 |
|---|---|---|
| 1 | `productId` + `productVersion` | **正式产品标识与版本**（**名称相同但版本不同不可拼接**） |
| 2 | `serviceType` | 服务类型 |
| 3 | `problemsSolved` | **可解决的问题** |
| 4 | `applicableCustomers` | 适用客户 |
| 5 | `businessPurpose` | 业务用途 |
| 6 | `requiredDocuments` | **材料清单** |
| 7 | `conditions` | **条件条款**（见 §3） |
| 8 | `exceptions` | **例外条件** |
| 9 | `mutex` | **互斥关系**（见 §4） |
| 10 | `validity` | **生效期** |
| 11 | `sourceLocator` | **来源定位**（EvidenceSpan） |
| 12 | `explanation` | **解释文本** |
| 13 | `publicationStatus` | **发布状态** |

### 2.2 与既有 schema 的关系

**已核实**：以上 13 字段**无一本仓 schema 完整承载**。
现有 `field-assertion` / `evidence-ref` / `evidence-span` 可用于 `sourceLocator` 与条款断言，
但**`conditions` / `exceptions` / `mutex` / `requiredDocuments` 无对应 schema**。

**→ 设计结论**：WP04 需新增 ProductCard schema，**并复用**既有
`evidence-ref` / `evidence-span` / `field-assertion` 以保持血缘一致，
**不得另建一套独立可修改的同义定义**（§4.3 末段要求）。

## 3. 条件核验设计（§8.2，核心）

### 3.1 能力边界澄清（§8.2 原文，**必须严格照此**）

**允许**：依据批准规则形成「**当前证据下某项条件满足 / 不满足 / 未知**」
**禁止**：形成**正式银行客户准入、授信审批、额度承诺或定价决定**

> §8.2 特别提示：「如果现有合同中的"**不产生准入结论**"被解释为**连条件判断也禁止**，
> 应先**明确上述语义差异**，**不通过改一个展示名称暗中扩大权力**。」

**→ 我方处置**：我在外部调研提纲 Q3.3 曾把"不产生授信结论"当作已足够。
建议书指出**语义需澄清**（条件判断 ≠ 准入结论）。
**处置**：本条须走**显式语义澄清**，**不改名规避**；
澄清前，`SIM-CAP-PRODUCT-REC` 的 `boundary` 保持原义。

### 3.2 四态条件结果（§8.2）

| 结果 | 推荐处理 | 例子（§8.2 原文） |
|---|---|---|
| `TRUE` | 在**当前证据范围内**该条件满足 | 产品要求的企业存续期限已由**正确身份资料**证明 |
| `FALSE` | 该候选在本次模拟筛选中**排除**，**保留理由** | 本次用途不在条款允许范围内 |
| `UNKNOWN` | **不给"条件已满足"结论**，转成**资料缺口** | 缺少真实交易背景资料 |
| `ERROR` | **停止该候选判断**，报告执行问题 | 规则版本丢失、引用冲突或计算失败 |

**强制约束**：
- **全未知不进入"条件已满足"**（§9.1 CAP-07 实质验收原文）
- `ERROR` ≠ `FALSE`：**执行失败不得当作条件不满足**

### 3.3 排序规则（§8.2）

> 「推荐排序**仅在允许的候选集合中执行**。先考虑**客户已确认目标、业务适配、
> 证据充分性、服务成本与实施难度**，**再**考虑本行经营价值；**明确排序依据**。
> **不要为凑齐三个候选展示不适用产品**，**也不要把 LLM 自评分当校准后的成功概率**。」

| 排序次序 | 依据 |
|---|---|
| 1 | 客户已确认目标 |
| 2 | 业务适配 |
| 3 | 证据充分性 |
| 4 | 服务成本与实施难度 |
| 5 | 本行经营价值（**最后**） |

**禁止**：
- 凑数展示不适用产品
- LLM 自评分当作成功概率
- **只按本行中收排序**（§7.3 R12 原文）

## 4. 互斥关系设计（§8.3，**必须精确**）

### 4.1 正确 vs 错误写法（§8.3 原文）

| 写法 | 判定 |
|---|---|
| ✅ 「**同一笔应收不得在本次方案内重复作为两项冲突融资的基础**」 | **正确**：描述**对象 + 条件** |
| ❌ 「A 产品与 B 产品永远互斥」 | **错误**：笼统 |

### 4.2 事件阻断的边界（§8.3 原文）

> 「**异常事件是否阻断某产品，必须由产品规则决定**；
> **不能因为融资候选受限，自动禁止所有结算或服务沟通。**」

**→ 这是对我方 `SIM-XC-4`（自动升级为风险预警）的重要约束**：
即使 R08 触发 `RISK_EVENT`，**也不得**自动阻断结算类/服务类候选。
阻断范围**必须由产品规则显式声明**。

## 5. 首期产品设计（§8.3 演示条款）

> **注意**：§8.3 原文声明「以下"演示产品 A/B/C"**只用于说明目标合同**，
> **不覆盖现有 SIM-P001 等产品定义**。落地时应在受控产品版本中**明确采用或映射**。」
> → 故产品 A **不自动等同** `SIM-P001`。**须走受控映射**（`待核`）。

### 5.1 产品 A：周转融资准备

| 项 | 内容 |
|---|---|
| **服务问题** | 已识别经营周转需求 |
| **明确 SIM 条件** | ①主体匹配 ②用途为经营周转 ③所需财务材料有效 ④**当前本行逾期/欠息为零** ⑤**用途证据非 UNKNOWN** |
| **输出与边界** | 条件对照及材料清单；**不输出额度、承诺或正式授信通过** |

**条件 ⑤ 的关键设计**：**用途证据为 `UNKNOWN` 时，不得进入"条件已满足"**（§9.1 CAP-07）。

### 5.2 产品 B：应收融资准备

| 项 | 内容 |
|---|---|
| **服务问题** | 确定交易产生的回款等待 |
| **明确 SIM 条件** | ①A 中适用的基础条件 ②存在**已确认应收及交易背景** ③**权利归属可核验** ④**同一应收没有本次规则禁止的重复融资** |
| **输出与边界** | 逐条核验；**没有登记/证据就不能把"未见重复融资"判 TRUE** |

**条件 ④ 是 §8.3 明文的反例警示**：**"未见"≠"不存在"**。
这与 §4.3 的开放世界语义一致（OWL：**未记录某事实不等于该事实为假**）。

### 5.3 产品 C：代发服务沟通

| 项 | 内容 |
|---|---|
| **服务问题** | 企业希望改善工资发放 |
| **明确 SIM 条件** | ①主体和授权明确 ②**存在工资发放需求** ③服务地区/币种符合该 SIM 条款 |
| **输出与边界** | 讨论流程和材料；**不导出员工个人营销名单** |

**注意**：产品 C 的边界是**隐私边界**（§16.3-9「内部信息对外泄露」）。
与 E05 案例呼应：**不得将未覆盖员工全部认定为可营销个人**。

## 6. 知识体检（§8.1）

### 6.1 六项检查

| # | 检查 | 不通过时 |
|---|---|---|
| H-1 | **条款缺失** | 标记为"知识待完善项" |
| H-2 | **旧新版本冲突** | 拒绝进入可执行候选 |
| H-3 | **来源失效** | 拒绝进入可执行候选 |
| H-4 | **条件无法计算** | 拒绝进入可执行候选 |
| H-5 | **互斥关系无对象** | 拒绝进入可执行候选 |
| H-6 | **对客解释超出原文** | 拒绝进入可执行候选 |

### 6.2 处置差异（§8.1 原文，**关键**）

> 「体检**未通过**的产品**可以作为"知识待完善项"可见**，
> 但**不能进入可执行候选判断**。」

| 可见性 | 可执行性 |
|---|---|
| **可见**（列为待完善项） | **不可用于筛选/排序** |

**→ 这是"诚实但不越权"的精确设计**：既不隐藏缺陷，也不拿缺陷产品下判断。

## 7. 对客话术验收（§8.4）

### 7.1 五条可复核标准（§8.4 原文）

| # | 标准 |
|---|---|
| T-1 | 问题针对**明确角色可掌握**的业务事实 |
| T-2 | **一次主要询问一件事** |
| T-3 | **不预设**违法、经营恶化或产品适合 |
| T-4 | **不要求对方确认未经证明的数字** |
| T-5 | **说明需要何种资料** |

### 7.2 合格/不合格示例（§8.4 原文）

| 判定 | 文本 |
|---|---|
| ✅ 合格 | 「最近三个完整月，本行可见经营收款较比较期下降。**是否发生了收款渠道、主要客户账期或结算方式变化？**」 |
| ❌ 不合格 | 「**贵司营收下降是因为客户流失吧？**」 |

> **注意合格示例的三个特征**：
> ① 只说**本行可见**（不冒充全量）
> ② 陈述**已核实的事实**（下降）
> ③ 询问**开放式的可能原因**（渠道/账期/结算），**不预设结论**

### 7.3 自动检查的边界（§8.4 原文，**必须诚实**）

> 「自动检查**可发现**禁止承诺、无依据数字、角色错误和明显预设结论；
> **可回答性、礼貌和业务价值仍需有准则的人工抽样评价**。
> **不能宣称一组关键词检查已经穷尽语言边界。**」

**→ 这直接回答我在调研提纲 Q3.2 的自问**（「话术禁止诱导性提问**如何自动校验**？」）：
**答案是不能完全自动校验**。自动只能覆盖 4 类可机械判定的问题；
其余须**有准则的人工抽样**。

**我方此前设计缺陷**：`SIM-CAP-KYC-GAP` 规则含「话术必须客户可回答、禁止诱导性提问」，
**但未声明哪些可自动、哪些须人工**。**须补此声明。**
