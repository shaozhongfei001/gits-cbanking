## 2. 请求裁定/确认的 4 项事项

### 事项 C1（U-D）：仓库工作区存在**未提交的整仓重命名**

**观察事实**：

```
git status --porcelain  →  464 项
  D（删除）159 项：src/dkws/**、deploy/dkws-*、docs/*DKWS*
  ??（新增） 81 项：src/kert/**、deploy/*kert*、docs/*KERT*
  M（修改）224 项：改名引用同步
```

**性质判断**：这不是零散改动，而是 **`dkws` → `kert` 的仓级重命名重构**。

**GK-KE 的处置**：为判断该重构是否影响绑定结论，我方**比对内容而非提交号**：

```
git show HEAD:src/dkws/application/skills.py  与工作区比对
→ registry() 内容逐行一致
```

故 **U-B 绑定结论对重命名不敏感**，依据是源码内容（类名、方法名、常量名）。

**但仍请求 KERT 维护方**：

| # | 请求 |
|---|---|
| 1 | **确认**该重命名是有意为之（而非误操作） |
| 2 | **提交或存档**，使其可作为受控锚点 |
| 3 | 若为**分阶段重构**，告知预计完成时点 |

**理由**：未提交的工作区**不可作为受控证据锚点**，影响跨仓证据的可复现性。

**影响范围**：证据可复现性。**不阻塞**我方当前结论。

### 事项 C3：KERT 侧**产品推荐未拆分**

**观察事实**：KERT 侧仅有**单一** `bank-front-product-recommendation` 包（`SK-FRONT-007`），
**无独立的"知识体检"与"条件核验"两个提供者**。

**依据**：建议书 §9.2 原文要求：

> 「`bank-front-product-recommendation` → **CAP-06 + CAP-07**；
> **分开知识体检、条件核验和候选排序**」

**GK-KE 的处置**：我方**已在 GK-KE 侧拆分**为
`SIM-CAP-PRODUCT-DOCTOR`(CAP-06) 与 `SIM-CAP-PRODUCT-CONDITION`(CAP-07)。

**但产生一个后果**：

> **体检门禁（体检未通过的产品不得进入条件判断）无法在提供者侧强制，
> 只能在 GK-KE 编排侧强制。**

**请求 KERT 维护方确认**：

| # | 问题 |
|---|---|
| 1 | 是否有计划在 KERT 侧拆分该包？ |
| 2 | 若否，KERT 侧能否提供**"体检结果"与"条件结果"可区分的输出字段**？ |
| 3 | 当前 `candidates[].matchLevel`（`high\|combo\|pending`）是否足以区分这两种语义？ |

**影响范围**：能力契约的**结构层**完整性。**不阻塞**当前推进。

### 事项 C4：`SKILL.md` **未声明机器可读 schema**

**观察事实**：
- 所有 `bank-front-*` 包的 `SKILL.md` **frontmatter 均无** `inputSchema` / `outputSchema` 字段
- output schema 以 **markdown 文件**（`references/output-schema.md`）形式存在
- `_load_packages` 用**正则**抽取首个 ` ```json ` 代码块作为 `schema_hint`，**上限 2000 字符**

**后果**：

| # | 后果 |
|---|---|
| 1 | **不是机器可校验的 JSON Schema** —— 无法做结构性校验，只能作提示 |
| 2 | **2000 字符上限**可能截断复杂 schema |
| 3 | 跨系统（GITS↔KERT）**无法做契约漂移检测** |

**请求 KERT 维护方评估**：

| # | 问题 |
|---|---|
| 1 | 是否可为每包增加机器可读的 request/response schema 声明？ |
| 2 | 若暂不增加，**2000 字符截断**是否已有已知影响？ |

**影响范围**：建议书 §9.4「能力验收四层证据」中的**结构层**。
**不阻塞**当前推进，但**结构层证据不足**。
