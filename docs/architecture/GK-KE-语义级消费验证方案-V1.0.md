# GK-KE：语义级消费验证方案（**预注册**）V1.0

> 出具：GK-KE 全局 Tech Lead｜日期：2026-09-13
> 目的：在**真实 LLM 接入之前**把判定标准定死，防止届时"标准随结果调整"
> 依据：建议书 §9.3 / §6.5 / §14.2 第 6 项
> **性质：预注册（pre-registration）。判定标准先于执行锁定，执行后不得修改。**

---

## 0. 为什么需要"预注册"

### 0.1 直接原因

我在本项目已多次**在拿到结果后调整判据**：

| # | 发生的事 | 性质 |
|---|---|---|
| 1 | 探针 PASSED 由我写的静态标志决定 | 判据由结果倒推 |
| 2 | 编译门禁写成永不失败 | 修改门禁以迎合结论 |
| 3 | 指标一律求和冒充"按公式复算" | 用统一动作掩盖差异 |

**若语义验证的标准在真实 LLM 接入后才定，第四次几乎必然发生。**

### 0.2 机制

```
本方案定稿 → 计算 SHA-256 → 写入 _preregistration.json
                                  ↓
              真实 LLM 接入后执行验证
                                  ↓
        执行结果与锁定标准比对；标准**不得修改**
                                  ↓
        若确需修改 → 必须新发版本并**保留旧版作为对照**
```

## 1. 语义级消费的**定义**

### 1.1 什么叫"语义级消费"

> **上游的**分析内容**（而非仅字段结构）改变时，下游的**结论**随之改变，
> 且改变方向符合合同规定。**

**与"输入级消费"的区别**：

| 层级 | 含义 | 现状 |
|---|---|---|
| **输入级** | 上游字段被传入下游输入 | ✅ **已证明**（`chain-trace`） |
| **语义级** | 上游**内容**变化使下游**结论**变化且方向正确 | ❌ **未证明** |

### 1.2 为什么现在证不了

确定性适配器产出**占位内容**（`indicators`/`conflicts`/`kycGaps` 恒为空），
故"下游因上游内容得出不同结论"**在本环境无法产生**。

**→ 需真实 LLM 才能执行。故本方案先行锁定标准。**

## 2. 判定项（**S1–S5，锁定**）

### S1 冲突传递

**条件**：上游 `conflicts` 非空（含具体 `conflictId` 与类型），且 `status=SUCCESS`、覆盖充分。

**预期**：下游输出中存在**可追溯到该冲突**的条目 ——
其 `trigger` / `evidenceRefs` / `basis` 引用该上游 `conflictId`。

**判据**：
```
存在下游条目 d，使得 upstream.conflicts[i].id ∈ d 的证据引用集合
且 d.verifyScript.factBasis 陈述与该冲突类型一致
```
**不通过的形态**：下游产出与冲突无关的通用缺口（说明未消费内容）。

---

### S2 空结论的正确解读

**条件**：上游 `conflicts=[]` **且** `status=SUCCESS` **且** 必需规则全覆盖。

**预期**：下游**不得**产出该冲突相关缺口（因为确实"未发现"）。

**判据**：
```
下游输出中不存在引用「已覆盖规则」对应冲突的缺口
```
**说明**：此条与 S3 成对，用于区分"真的没有"与"没查"。

---

### S3 未执行 ≠ 无冲突（**最重要的一条**）

**条件**：上游 `conflicts=[]` **但** `status ∈ {NOT_RUN, FAILED}`（或覆盖不足）。

**预期**：下游**必须**产出"覆盖不足 / 待核实"，**不得**判"无冲突"。

**判据**：
```
下游输出中存在 reason ∈ {COVERAGE_INSUFFICIENT, COVERAGE_NOT_REPORTED, VERIFY_REQUIRED}
且 下游**未**出现「未发现冲突」类肯定表述
```
**依据**：§6.5「未执行过的『无冲突』与检查成功且未发现冲突必须区分」；
§9.3 表行 2「FAILED/NOT_RUN 不能当无冲突」。

**为何最重要**：它是**唯一一条要求"下游不做某事"的判据**，
最能检验下游是否真正理解上游状态 —— 也是最容易被"看起来对"糊弄过去的一条。

---

### S4 假设不得关闭缺口

**条件**：上游提供 `explanations`，其中某条**无 `evidenceRefs`**。

**预期**：下游保留该事项为**假设**（`HYPOTHESIS`），**不得**据此关闭缺口。

**判据**：
```
下游存在该事项的条目，其状态为 HYPOTHESIS / 待核实
且 下游**未**将该事项标记为已解决/已关闭
```
**依据**：§7.2 步骤 5「区分解释已验证与仅有解释假设」；§7.6「解释须有证据」。

---

### S5 可复现

**条件**：**相同输入**连调两次。

**预期**：下游输出**一致**（或差异仅为允许的随机字段，如 `generatedAt`、`executionId`）。

**判据**：
```
排除允许字段后，两次输出 JSON 规范化后完全一致
```
**依据**：§10.3「同一固定快照应得到同一计划摘要值」。

## 3. 通过规则（**锁定，不得事后调整**）

| 结论 | 条件 |
|---|---|
| **语义级消费达成** | **S1–S5 全部通过** |
| **语义级消费未达成** | S1–S5 中**任一**失败 |
| **无法判定（INCONCLUSIVE）** | 适配器无分析能力，或无法产生 S1/S3 所需的输入差异 |

**关键约束**：

> **「无法判定」不得记为「通过」。**
> **「部分通过」不得表述为「基本达成」。**
> **通过项与失败项必须逐条列出，不得只报汇总。**

## 4. 防自证规则（**针对我方前科**）

| # | 规则 |
|---|---|
| **G-1** | **执行者与判据作者不得为同一人**。判据由本 TL 预先锁定；**执行由独立 QA 或另行指定的角色完成** |
| **G-2** | **不得修改被测对象以迎合判据**。若某能力不满足 S1–S5，正确做法是修能力或记录未达成，**不得放宽判据** |
| **G-3** | **不得删除失败用例**。失败用例须保留并计入统计 |
| **G-4** | **判据变更须留痕**。任何对 S1–S5 的修改必须新发版本，且**旧版保留为对照** |
| **G-5** | **不得以"模型波动"为由重跑到通过**。若因波动不通过，须**提高重复次数并报告全部结果**，而非选择性重跑 |
| **G-6** | **不得只报通过率而不报用例明细** |

**G-1 是本方案的承重规则** —— 前三项错误（静态标志、永不失败的门禁、统一求和）
**根因都是"作者即执行者"**。

---

## 6. 本方案的**边界**

- 本方案**不构成**语义级消费的任何达成声明
- 本方案**不修改**现有验证脚本；它**新增**一个待执行的标准
- S1–S5 **未经真实 LLM 检验**，其**可执行性本身是待验证的**
- 若执行时发现某条判据**技术上无法观测**，正确做法是**记录该条无法执行**，
  **而非删除该条以让整体通过**
