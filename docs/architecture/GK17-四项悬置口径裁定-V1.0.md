### 1.1 事实（实测，不可协商）

### 1.2 计数口径（**已用命令核实**，含本件起草期的一次自纠）

可复制复核：

```
python3 -c "import json;d=json.load(open('specs/knowledge-architecture/instances/product/UNRESOLVED.json'));print(len(d['unresolved']), d['unresolvedReferenceCount'])"
⇒ 40 40        （长度与自报一致）
```

**自纠记录（本件起草期）**：TL 起草时**凭阅读印象**将 `unresolved[]` 记为 38 条，

**本件后续一律采用**：40 条引用 / 12 个唯一符号 / 13 张卡 / 0 条关系实例，

### 1.3 裁定：**维持既有裁定，不新建映射表**

沿用 `GK17-产品卡引用空间裁定-V1.0.md` §2 / §5 的口径：

1. 三个关系字段的**合法取值空间 = `PROD-*`**（收紧，非放宽）；

## 2. ② `legal_entity` 字段口径：**file-first SSOT 为权威，运营库为投影**

### 2.1 事实（三处，决定性证据已存在）

| 侧 | 位置 | 内容 |
|---|---|---|
| 运营库 | `adapters/persistence-relational/src/main/resources/db/migration/{h2,mysql}/V003__customer_context.sql:32` | `CREATE TABLE IF NOT EXISTS legal_entity` |
| 场景包 | `scenario/seed/02_master_data/legal_entities.csv` | file-first 数据文件 |
| **场景包自述** | `scenario/seed/14_database/DATA_MODEL_NOTES.md:3` | 「**Canonical data is file-first**：V1.1 包中的 JSON/JSONL/CSV 是场景 SSOT；**MySQL 脚本只作为开发适配**」 |

### 2.2 裁定

> **权威源 = file-first SSOT（`scenario/seed/**`）**；**运营库（Flyway 迁移建的表）= 投影 / 开发适配**。

**依据**：本仓的权威流本就单向且 file-first（`specs/` 为合同 SSOT，`generated/` 为派生物；
知识架构侧 `assets/**/*.md` 的 front matter 是权威而非 registry）。场景包自述与之一致。
若反过来以运营库为权威，则**同一实体在场景包与 DB 各有一份定义**且 DB 需人工同步 ⇒ 必然静默漂移。

**对 `WP3.2` 的实现口径**（可执行）：

1. A-Box 个体**从场景包导出**，**不读运营库**；
2. 运营库表中的同名字段被视为**投影**，不得作为导出输入；
3. **同类问题一并适用**：`credit_facility`、`commitment`（Tick 6 实测同类）；
4. 若未来需要 DB→场景包 反向流，须**另立合同 + 门禁**，不得默许双向可写。

### 2.3 保留给数据映射 Owner 的一项

**若**数据映射 Owner 认为运营库存在场景包未覆盖的字段，须**显式提出差异清单**，
走合同先行（`specs/data/source-contract.schema.json` 侧）增补；**本件不预先假定**。

## 3. ③ `Account` / `Document` 的权威物理源：**不造类，指定承担者**

### 3.1 事实

- `find . -name "Account.java" -o -name "Document.java"` ⇒ **零命中**（GITS 侧无系统类）；
- 账户的唯一实据落点：`modules/operational-ontology/.../Transaction.java:28` 的 `accountId`（仅作为**引用**出现）；
- 文档的唯一实据落点：`gits:Evidence` 的 `sourceUri`（`specs/semantic/gits-core.linkml.yaml:66`）；
- 设计点名的 §4.3 对象（账户/产品/文档/能力）**均已按"域引用类"模式处理**（W1-INPUTS §A.3）。

### 3.2 裁定

> **不为 `Account` / `Document` 新建本体类，也不新建 Java 类、不发明任何字段。**
> 二者**身份由已有字段承担**：

| 设计对象 | 身份承担者 | 编号空间 | 说明 |
|---|---|---|---|
| **账户** `gits:Account` | `Transaction.accountId` | 沿用其现有取值 | 若未来需要账户独立身份，须**先有权威物理源**再建模（走合同先行） |
| **文档** `gits:Document` | `gits:Evidence.sourceUri` | 沿用 URI | 裁定「文档身份由 `Evidence.sourceUri` 承担」，**不另立类** |

**依据**：本仓硬约束——**"GITS 侧无对应系统类者不得凭空造字段"**（W1-INPUTS §A.3 明文），
与 `gits:Customer` → `EDWCRM.A_ZHCX_CUST_BASE` 的既有先例同一模式。

**⚠️ 已知的诚实声明**：`Transaction.accountId` **不是**权威账户主数据，只是一个**引用**。
本裁定**不声称**账户实体已建模；只声明"当前不造类，身份由此字段承担"。

## 4. ④ 两道环境红：**不在 GK17 内拆门禁，另立 Loop**

### 4.1 事实（复现）

| 门禁 | 现象 | 根因 |
|---|---|---|
| `frontend_test` | `make frontend-test` ⇒ FAIL | 沙箱 safe-delete 守卫拦截 `npm ci` 的 538 文件批量删除（`SAFE_DELETE_BULK_CONFIRM_REQUIRED`，阈值 500） |
| `backend_test` | `make backend-test` ⇒ FAIL | 走 `./mvnw verify`；OWASP `dependency-check` 绑在 `verify` 阶段且需**联网**拉 RetireJS。<br>⚠ **口径更正（Tick 19，由独立 QA 指出，TL 已实测复核）**：原写"端点**不可达**"**过强**。实测为 **RetireJS 端点间歇性超时**（与时间相关）：<br>· **本 Loop evidence 中有一次全绿** —— `evidence/backend_test-20260915T002338Z.log`：`BUILD SUCCESS`、**0 模块 SKIPPED**、`Analysis Complete`、`dependency-check-guard: all 15 report(s) PASS`；<br>· TL 于 2026-09-16 重试（`evidence/backend_test-20260916T134510Z-W8-RETRY.log`）**仍红**，同型报错 `UpdateException: Failed to initialize the RetireJS repo`、**14 个模块 SKIPPED**、`BUILD FAILURE`。<br>⇒ **形态是「1 次全绿 + N 次红」，不是确定性不可达。** 但**本次仍红 ⇒ 仍不得计为通过**，`exit_criteria.dev` 仍未满足 |

### 4.2 裁定

> **GK17 不拆、不改这两道门禁。** 理由：GK17 的 `LOOP.yaml.scope.exclude` 已明文排除改动门禁构成；
> 且这两道门禁被**全部 Loop 共用**，改动会**外溢到其他执行者**（与 Tick 10 拒绝登记 `run_gates.py` 同一理由）。

**处置**：
1. GK17 收口时把两道红**如实记为 `ENVIRONMENT_LIMITATION`**，**不**计为通过、**不**弱化判据；
2. **另立一个小 Loop**（建议 ID：`GK18-test-gate-decoupling`）专做「单元测试面 与 联网漏洞库 解耦」，
   scope 仅限 `Makefile` + `pom.xml` 的 profile 划分，**不改任何测试断言**；
3. 该 Loop 须有**独立的门禁前置条件**（P1–P5，见编排表 §0.1），否则会重演"红读不出信息"。

**测试面现状口径（GK17 内继续沿用）**：用 `./mvnw --batch-mode --no-transfer-progress test`
