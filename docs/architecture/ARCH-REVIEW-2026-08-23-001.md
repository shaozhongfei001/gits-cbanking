## 5. MAJOR 发现

### ARCH-M01｜CI 工作流本身不可形成可靠质量门禁

1. Unit/Integration job 使用 `-pl apps/api` 而没有 `-am`；GitHub job 彼此隔离，内部 SNAPSHOT 模块不能依赖前序 job 的 `target/`。
2. Frontend CI 使用 Node 20，仓库 `engines` 和 README 要求 Node 22+。
3. `frontend/package-lock.json` 与依赖解析不同步，标准 `npm ci` 已失败；历史 QA 通过依赖隐藏环境变量 `NPM_CONFIG_LEGACY_PEER_DEPS=true`，未固化为受控工程约束。
4. E2E job 只由 Playwright 启动 Vite，未启动后端；测试却调用代理到 `127.0.0.1:8082`。
5. E2E 的上游 Docker job只“构建镜像”，没有运行 API 容器，且不同 job 不共享运行进程。
6. CI 没有执行 `make generate/check/framework-test/tooling-test`，知识合同与语义规则门禁不在主合并链。

### ARCH-M02｜合同—实现一致性门禁存在“假检查”

1. CI 的 Contract Index job grep `path:`，而注册表实际字段为 `authority_source`；本次独立复核显示它检查了 **0** 个引用仍输出 PASS。
2. `ContractComplianceTest.openApiEndpointsHaveControllerImplementations()` 没有扫描 Controller，也没有比较 method/path，只检查 OpenAPI 每个 path 至少有一个 HTTP method。
3. 该测试注释仍写“目前 spec 只有 `/architecture/status`”，实际已有 49 paths/57 operations，明显陈旧。
4. `make check` 能证明“合同源与 generated 一致”，不能证明“Controller/DTO/错误码与 OpenAPI 一致”。

### ARCH-M03｜知识控制平面尚未真正吸收到业务主链

1. `ActivationPlannerPort` 虽注册为 Spring Bean，但生产代码没有消费者；仅在测试中调用 `.plan()`。
2. `DefaultContextAssembler` 仅在模块测试/机制测试中实例化，未进入实际 API 业务链。
3. `KnowledgeWikiService` 仅有测试，没有生产 Bean 或调用者。
4. P23 的 `KnowledgeDrivenPrevisitReportGenerator` 直接硬编码 `PREVISIT_KNOWLEDGE_SCOPE`，没有使用 ActivationPlan 决定范围。
5. 实际业务链读取 ActivationContract 的 KI 列表，但绕过 route policy、plan、permission decision 和 evidence bundle。

因此，“可编译合同”和“运行控制面组件”已经存在，但“业务调用严格受计划控制”的核心设计尚未闭合。

### ARCH-M04｜LLM grounding 的 fail-closed 语义与代码不一致

1. `KnowledgeWikiService` 在知识地图为空时仍调用 LLM，并提示使用通用领域知识；这属于带披露的降级，不是 fail-closed。
2. `KnowledgeAssembler` 在 KI/KE 缺失时静默跳过，仍可生成空/不完整上下文。
3. `KnowledgeDrivenPrevisitReportGenerator` 在激活合同缺失时返回空 KI 列表，仍继续调用 LLM。
4. LLM JSON 采用字符串定位和逗号分割，不使用 JSON parser/schema；转义、逗号、嵌套数组会误解析。
5. 生成的策略/问题/风险没有携带知识元素 ID、证据引用、版本或内容 hash，无法逐项解释。

对银行客户经营场景，这些问题可能把未受控推断混入正式报告草案。应按任务风险区分 `FAIL_CLOSED`、`DEGRADE_WITH_DISCLOSURE` 和 `OPTIONAL_SKIP`，并由合同强制执行。

### ARCH-M05｜产品推荐子系统仍是规则演示，不是综合方案引擎

`ProductMatchingService` 当前只有 5 条硬编码启发式规则：大额结算、定期还款、现金流波动、高新研发、出口描述。它存在以下关键缺口：

- 未使用产品知识卡或产品版本；
- 未执行客户/区域/机构/额度/期限/币种/担保/贸易背景准入；
- 未检查产品依赖、替代、冲突和重复占额；
- 未生成产品组合、A/B/C 方案、价值测算或实施顺序；
- 以行业和企业规模直接推断“存在融资需求”；
- 注入的 `KycInsightService` 未使用；
- 推荐结果没有证据、规则版本、待确认项、人工审核状态；
- 接口可直接返回“建议产品”，容易让演示性规则被误解为正式银行推荐。

成熟度只能评为 `M1_RULE_PROTOTYPE`，不得对应产品基线中的完整 M20 能力。

### ARCH-M06｜知识资产路径和适配器状态仍漂移

远端 `main` 的事实与 Tech Lead 清理目标一致，但尚未整改：

- 13 个资产 `source.uri` 仍指向已迁移的 `scenario_data/`；
- `scenario_data_promopt.md` 仍存在；
- 5 个资产声明 `skill-runtime-adapter`，实现目录不存在；
- 2 个资产声明 `mock-rag-adapter`，实现目录不存在；
- `ADAPTER_STATUS.md` 不存在；
- `modules/skill-runtime`、`adapters/mock-rag` 不存在；
- `knowledge-filesystem` 仍是当前 API 的真实编译和运行依赖，不能在无等价替代验证时直接删除。

### ARCH-M07｜安全与生产硬化仍不闭合

1. 基础 `application.yaml` 配置 `server.error.include-stacktrace: always`，prod 未覆盖为 `never`，存在生产错误信息泄露风险。
2. API key rotation deadline 解析失败时只告警并按 `null` 处理，轮转 key 会无截止期继续有效，属于配置失败后的 fail-open。
3. 单一共享 API Key 不是银行 IAM/RBAC，仓库也已明确真实 IAM 未接入。
4. OWASP suppression 前三项缺少自身规则要求的审批人/有效期；若干 suppression 描述已过时。
5. nanoid suppression 注释称“无任何 5.x 声明”，实际根 lockfile 包含 `nanoid@5.1.16`；虽可能是已修复版本，但证据描述不准确。
6. secret scan 仅扫描当前工作树，不覆盖完整 Git 历史；公共仓库下需要历史 secret/PII 扫描。

### ARCH-M08｜架构边界没有机械验证

项目依赖 Spring Modulith，但未发现 `ApplicationModules.verify()` 或等价架构测试。当前“领域模块无基础设施反向依赖”“模块边界清晰”主要靠约定和代码审阅，不是持续门禁。

### ARCH-M09｜仓库制品与源代码混杂

- 已跟踪的 `frontend/dist/index.html` 引用未入库的 JS/CSS hash 文件，本身不可运行；
- 提交了旧 bundle、`docs/test.docx`、大量截图和生成制品；
- `scripts/data_snapshot.json` 约 4.9MB，并有多个文档生成脚本依赖工作目录隐式读取；
- 生成物、证据、可执行发布物、历史归档和源代码的生命周期没有完全分离。
