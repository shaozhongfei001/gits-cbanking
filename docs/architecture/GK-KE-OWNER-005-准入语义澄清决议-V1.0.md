## 1. 为什么必须澄清（建议书 §8.2 原文）

> 「建议将能力边界澄清为：**允许**依据批准规则形成『**当前证据下某项条件
> 满足 / 不满足 / 未知**』；**禁止**形成正式银行客户准入、授信审批、额度承诺或定价决定。
>
> 如果现有合同中的『**不产生准入结论**』被解释为**连条件判断也禁止**，
> 应先明确上述语义差异，**不通过改一个展示名称暗中扩大权力**。」

**→ 问题实质**：既有合同多处写「不产生准入结论」，但**未定义"准入结论"是否包含
"条件满足/不满足"这一判断**。若包含，则能力根本无法工作（无法判断任何条件）；
若不包含，则须**显式澄清**，否则后续实现会产生歧义。

## 3. Owner 决议：语义边界（**本条为裁定，不得再作扩张解释**）

### 3.1 允许（PERMITTED）

能力**可以**输出，且**应当**输出：

| 允许的输出 | 语义 |
|---|---|
| `条件满足`（TRUE） | **在**当前证据范围内**该条件满足 —— 非正式准入 |
| `条件不满足`（FALSE） | 该候选在本次模拟筛选中排除，保留理由 |
| `条件未知`（UNKNOWN） | 证据不足，转为资料缺口 |
| `条件执行错误`（ERROR） | 规则缺失/引用冲突/计算失败，停止该候选判断 |
| `证据与条款对照结果` | 逐条条款 vs 证据的对照 |
| `资料缺口清单` | 补齐条件所需的材料 |
| `候选方向与排序依据` | 讨论方向，非推荐决定 |

### 3.2 禁止（PROHIBITED）

能力**不得**输出：

| 禁止的输出 | 说明 |
|---|---|
| **正式银行客户准入决定** | 是否接纳该客户为银行客户 |
| **授信审批结论** | 是否批准授信 |
| **额度承诺** | 具体授信金额 |
| **利率定价** | 具体价格 |
| **"已批准"/"已通过"表述** | 任何暗示正式决定完成的状态 |
| **把条件 TRUE 表述为"符合准入"** | **关键**：条件满足 ≠ 准入通过 |

### 3.3 关键区分（**本次裁定的核心**）

```
条件判断（允许）        正式准入决定（禁止）
─────────────────      ────────────────────
当前证据下该条件满足     银行决定接纳该客户
可被证据推翻            须授权主体作出决定
输出 KNOWN/UNKNOWN     输出批准/拒绝
面向客户经理准备        面向正式业务流程
```

> **"条件满足"不蕴含"准入通过"。** 前者是**证据状态**，后者是**银行决定**。
> 二者**主体不同、可推翻性不同、后续流程不同**。

### 3.4 对既有措辞的处理方式（**不改名规避**）

依 §8.2「**不通过改一个展示名称暗中扩大权力**」：

| 处置 | 说明 |
|---|---|
| **不改既有文件的措辞** | `SIM-CAP-EIGHT-DIM.json` / `SIM-CAP-KYC-GAP.json` 原文**保留** |
| **新增解释性条款** | 在受影响能力中**新增** `admissionSemanticsClarification` 字段，**指明**该澄清的依据与范围 |
| **不追溯改写历史** | 既有措辞在**其原语境下仍然有效**（指禁止正式准入决定） |

**→ 即：不是"把禁止改成允许"，而是"澄清禁止的范围本来就不含条件判断"。**

## 4. 澄清的适用范围（**明确边界，防止被扩大解释**）

| 适用 | 不适用 |
|---|---|
| `SIM-CAP-PRODUCT-CONDITION`（条件核验） | 任何涉及**客户准入决定**的流程 |
| `SIM-CAP-PRODUCT-DOCTOR`（体检结论） | 授信审批系统 |
| `SIM-CAP-KYC-GAP`（缺口判断） | 反洗钱法定尽职调查 |
| `SIM-CAP-FACT-RECON`（事实对照） | 风险等级正式认定 |
| `SIM-CAP-EIGHT-DIM`（行业研判） | 额度/定价决定 |

**本澄清仅适用于 GK-KE SIM 范围内的访前准备链路，不延伸至任何生产业务决定。**
