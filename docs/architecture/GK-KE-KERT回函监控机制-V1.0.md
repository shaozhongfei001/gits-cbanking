## 2. 我的监控设计：三档机制

### 第 1 档：**主动轮询**（可立即启用）

我可以**定期只读检查** KERT 侧的可观测信号：

| 检查项 | 方法 | 含义 |
|---|---|---|
| HEAD 是否变化 | `git log -1` | 有提交 = 有进展 |
| 未提交改动数是否变化 | `git status --porcelain \| wc -l` | 从 464 减少 = 重命名在推进 |
| `skills.py` mtime / hash | `stat` / `sha256sum` | 变化 = R-3 可能在处理 |
| 新增回函文件 | 搜索 `*回函*` / `*LETTER*response*` | 直接信号 |
| `src/dkws` 是否被提交删除 | `git log --diff-filter=D` | U-D 进展 |

**机制**：写成脚本 + **触发本地通知**（不打扰 KERT）。

**局限**：
- 只能看到**代码层**变化，看不到**决策层**进度
- 若 KERT 在**独立分支/本地**工作，**看不到**
- **"没变化"不能推断"没在做"**

### 第 2 档：**设立可追踪的收件机制**（需你或 KERT 配合）

把函件从"文档留档"升级为**有回执的工单**：

| 方案 | 机制 | 需要谁配合 |
|---|---|---|
| **A** | 在 KERT 仓建立 `docs/inbox/GK-KE-<编号>.md`，**由 KERT 维护方**在其中写回执 | KERT 维护方 |
| **B** | Owner 转达，并约定**回函期限**（如 3 个工作日） | **Owner** |
| **C** | 若两仓有共享的工单系统，登记为受追踪事项 | 项目侧 |

**我建议 A + B 组合**：
- A 让回函**有固定落点**（我可只读轮询该路径）
- B 让回函**有期限压力**（避免无限等待）

**注意**：方案 A **不违反跨仓只读边界** —— 因为**写入方是 KERT 维护方**，
不是我。我只是**读取**该路径。

### 第 3 档：**升级触发**（何时必须打断你）

我不应无限期被动等待。**设明确的升级条件**：

| 触发条件 | 我方动作 |
|---|---|
| 超过约定期限（建议 **5 个工作日**）无回函 | **主动向你报告**，请你裁定 |
| KERT 侧出现**任何**相关变化 | **立即复核并更新能力状态** |
| KERT 回函**拒绝**某事项 | 评估影响，报告替代方案 |
| KERT 回函**暂缓** | **如实标注"待 KERT 答复"**，`callable` 保持 `false` |
| KERT 侧**长期无响应** | 提请 Owner 决定：**搁置** / **另寻路径** / **接受范围收缩** |

## 3. 关键纪律：**不把"沉默"当"同意"**

这是本机制**最重要的一条**：

> **若 KERT 不回函，`SIM-CAP-REPORT-ASSEMBLE` 的 `callable` 永远保持 `false`，
> 计划编译永久 `BLOCKED`，OC-04 永久不达标。**

**理由**：若把沉默当同意，就等于**单方面替 KERT 裁定 R-3**，
这会违反：
- AGENTS.md「不得凭名称/近似认定兼容」
- 建议书 §9.2「文档存在、包可加载、代码有同名字符串**都不是**语义兼容的充分证据」

**这与 FAIL-2026-09-12-04（把"未执行"当"无冲突"）是同一类错误**：
**把"未知"当成"已知"。**

- ❌ 不因等待而虚报进展
