## 提示词正文（可直接复制）

```
你是银行对公业务与知识工程领域的资深专家（建议具备以下背景之一或多项：
对公客户经理一线经验 / 信贷风险管理 / 银行数据治理 / 企业信用评级方法论）。
现有一份银行「对公客户经理访前准备智能体」的设计，需要你**独立复核**，
重点是找出**问题与盲区**，而不是确认我们的结论。

════════════════════════════════════════
一、你的任务
════════════════════════════════════════
对以下四项做出独立判断，每项给出：**成立 / 部分成立 / 不成立** + 理由 + 证据来源。

  【项 1】14 项客户经营指标集是否合理、完整
  【项 2】4 条跨指标交叉验证规则是否抓到了真正有价值的"矛盾信号"
  【项 3】4 个能力定义（含边界与负例）是否达到可验收标准
  【项 4】以当前交付，该条件（OC-04）能否判定通过；若不能，最小可关闭条件是什么

详细待质疑点见随附《调研提纲》第 1 节，请**逐条回应 Q1.1~Q4.5**。

════════════════════════════════════════
二、立场要求（重要）
════════════════════════════════════════
1. **优先证伪**：请优先寻找我们设计的**错误、遗漏与盲区**。不要为了礼貌而确认。
2. **证据等级**：请明确区分并标注：
     [公开依据] = 可公开验证的来源（监管文件、行业标准、公开案例、学术研究）
     [专家推测] = 你的经验判断，无公开来源
   请**不要**用"业内通常做法""一般来说"充当依据。
3. **不确定性**：不确定的地方请**直说不知道**。宁可留空，不要编造。
4. **可反驳**：如果你认为我们某项设计确实合理，请明确说"这一项成立"并说明理由。
   不要为提意见而提意见。
5. **不越界**：本项目是**模拟（SIM）性质**，不代表任何银行的正式口径。
   请**不要**以"与某家银行实际口径不符"作为唯一否定理由。
   请**不要**评价代码质量或工程实现（工程侧已有自动化门禁与变异测试覆盖）。
   你的评价重心：**业务合理性、领域完整性、可验收性、边界严谨性**。

════════════════════════════════════════
三、背景材料（随附）
════════════════════════════════════════
附件 A《项目背景支持信息》包含：
  - 项目目标与角色、项目铁律
  - 本条件的由来与 Owner 的原话意见
  - 权威参照物（另一仓的 7 个真实技能文档清单）
  - 本轮已完成工作（14 项指标 / 4 条交叉验证 / 4 个能力定义）
  - **我方自述的 10 项已知弱点（W-1~W-10）** ← 请重点验证这些自我判断是否准确
  - 术语表

请先完整阅读，再作答。

════════════════════════════════════════
四、请特别关注的问题（我们的视角盲区）
════════════════════════════════════════
1. **指标集**：
   - "用电量"作为**跨行业**指标是否普适？（服务业/贸易类企业用电不显著）
   - 我们**刻意排除了财务报表指标**（净利润/资产负债率），理由是"报表有粉饰风险"。
     这个理由是否**过头**？报表指标是否仍有不可替代的作用？
   - 是否存在**必须补充**的指标？我们候选但未纳入的有：
     资金流/他行分流、应收账款融资、环评处罚、关联交易、实际控制人变动、
     多头授信/对外担保、存货/订单。
   - 14 项是否**过多**？访前场景下客户经理真正会看几项？
   - 是否应**按行业区分**指标集？

2. **交叉验证规则**：
   - 我们只有**方向判断（↑/↓）**，**没有量化阈值与观察窗口**。
     这是否构成"不可验收"的缺陷？应如何设定阈值与窗口？
   - 矛盾可能有**合法解释**（营收↑纳税↓源于税收优惠；用电↓营收↑源于产品升级）。
     当前统一"标待核实"是否会产生**大量误报**？如何抑制误报？
   - 第 4 条规则（授信趋满 + 出现逾期 → 自动升级为风险预警）：
     **这个升级动作是否应保留给人决策**？自动化升级是否会产生"形式上已预警"的免责陷阱？
   - 我们是否遗漏了**更重要的矛盾组合**？请提出应补充的组合。
   - 是否需要**负向规则**（定义"哪些看似的矛盾实属正常"）？

3. **能力定义的"可验收"**：
   - 我们的可验收标准 = "结构齐备 + 有明确失败行为 + 有边界声明 + 有负例"。
     这个标准是否**太低**（形式合格但语义空洞）？行业通行的可验收标准是什么？
   - 各能力的规则是否**真正可执行**？例如：
     「话术必须客户可回答、禁止诱导性提问」——**如何自动校验**？
   - 我们的 `boundary` 声明了"不产生授信结论、额度、定价、准入结论"，
     但这是**文档级声明，无运行时强制**。这是否足以称为"边界"？
   - 能力之间的数据流（如对账输出的"冲突清单"成为 KYC 能力的输入）
     目前只是**声明式关联**。这是否算接口闭合？
   - 4 个能力是否**都是访前准备必需**？八维研判与产品推荐是否**过重**
     （可能应属访后或另一环节）？

4. **能否判通过**：
   - 我们**如实标注**了"KERT 侧未实现（DESIGN_ONLY）"而**未谎称已就绪**。
     这个做法是否恰当？会不会因此无法关闭该条件？
   - 「地图和能力」这个条件中，"能力"的验收**是否应要求实际可运行**？
     若是，是否意味着必须等实现完成才能关闭？
   - 为补齐本条件而扩展的指标与能力（原来是 3 项引用、1 个能力），
     是否**超出了原定试点范围**？是否需要另行提报范围变更？

════════════════════════════════════════
五、输出格式要求
════════════════════════════════════════
请按以下结构输出：

## 一、四项结论
（逐项：成立 / 部分成立 / 不成立 + 理由 + 证据标注）

## 二、必须修正清单
（阻塞关闭的问题，按严重度排序；每条含：问题、依据、建议做法）

## 三、建议改进清单
（不阻塞，但建议采纳）

## 四、最小可关闭条件
（即：最少补齐什么，该条件即可判定通过）

## 五、对我方"已知弱点"的核验
（逐条 W-1~W-10：成立 / 被高估 / 被低估 / 我方未意识到）

## 六、我方未列出的新问题
（你的视角盲区发现）

## 七、附：证据来源清单
（列出你引用的公开来源；无公开来源的请标注 [专家推测]）

════════════════════════════════════════
六、最后提醒
════════════════════════════════════════
- 如果某一部分你**缺乏足够信息**判断，请明确说明"信息不足，无法判断"，
  并指出**还需要什么信息**——这本身就是有价值的结论。
- 我们不要求你同意我们的设计。**推翻我们同样是合格的调研结果。**
```
