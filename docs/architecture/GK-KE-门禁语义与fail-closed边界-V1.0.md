## 1. 门禁语义：三类结果必须**分开阅读**

### 1.1 三类结果的定义

| 类别 | 含义 | 是否应导致 `make check` 失败 |
|---|---|---|
| **INTEGRITY**（完整性） | 合同/制品**损坏或违反自身声明**（schema 不符、hash 不匹配、枚举非法、时间泄漏…） | ✅ **必须失败** |
| **READINESS**（就绪度） | 制品完好，但**能力/链路尚未达到所需状态**（如能力不可调用、trace 缺失） | ❌ **不应导致门禁失败**（见 §2） |
| **NOT_APPLICABLE** | 该检查在当前范围**不适用**（如 L4-2 边界内的事项） | 不适用 |

### 1.2 为什么必须分开

> **若把"未达成"计入门禁失败，会产生一个结构性诱因：
> 为了让门禁变绿，最省力的路径不是补齐能力，而是把"未达成"改写成"未检查"或"不适用"。**

**这正是我先前犯过的错**（把静态标志当真实调用、把门禁写成永不失败）。
**门禁设计本身不应制造这种诱因。**

### 1.3 修正：门禁退出码语义

| 场景 | `make check` 行为 |
|---|---|
| 有 INTEGRITY 失败 | **非零退出**（必须修） |
| 无 INTEGRITY 失败，有 READINESS 未达成 | **零退出**，但**输出显著标注** `READINESS NOT MET: [...]` |
| 全部通过 | 零退出 |

**关键约束**：READINESS 未达成**必须被打印出来**，
**不得静默通过** —— 否则又变成"隐藏结论"。

**→ 即：`make check` 通过**不等于**"一切就绪"。
通过只表示"制品完整且就绪度已如实报告"。**

## 2. 就绪度应如何被门禁化（**替代方案**）

不把 READINESS 计入失败，**不等于**"没人管就绪度"。改为：

| 机制 | 作用 |
|---|---|
| `run_gates.py` 汇总表 | 每次 `make check` **打印** READINESS 未达成项 |
| `make readiness` 目标 | 单独运行就绪度检查，**非零退出**，供发布前把关 |
| `EVIDENCE.json` 的 `readiness` 字段 | 把当前就绪度**写入证据文件**，可追溯 |
| 收口决议文档 | 明确写"B 层未达成"，**不依赖门禁表达这一结论** |

**原则**：**结论由文档明确声明，门禁只负责暴露事实，不负责替人下结论。**

## 3. fail-closed 的真实 LLM 风险（QA 第 1 问）

### 3.1 风险描述

我在 KERT 侧加入的校验：`run_pkg` 输出**必须包含**该包 output-schema 声明的顶层键，
缺失即 `fail-closed` 拒绝返回。

**在确定性适配器下**：输出由我方生成，必然符合 → 无风险。

**在真实 LLM 下**：模型可能返回**不合 schema 的输出** → **请求被拒绝**。

### 3.2 风险评估（**诚实评估，不淡化**）

| # | 风险 | 严重度 |
|---|---|---|
| 1 | **真实模型输出波动导致偶发拒绝** | 中 |
| 2 | **长 schema（如 eight-dimension 18 个键）命中率更低** | 中 |
| 3 | 用户看到"调用失败"而非"部分结果" | 低-中 |

### 3.3 处置（**分层，不做一刀切**）

| 层 | 处置 |
|---|---|
| **当前** | 保持 fail-closed，**因为这是唯一能防止"调用成功但输出不符契约"泄漏的机制** |
| **建议（未实施）** | 真实 LLM 接入时，按**键重要性**分级：<br>· **必需键缺失 → 拒绝**（fail-closed）<br>· **可选键缺失 → 返回 + `warnings` 标注降级**<br>· 并在 `SKILL.md` 中**显式区分必需/可选键** |
| **前置条件** | 需 KERT 侧在 output-schema 中**声明键的必需性**（当前 schema 未区分） |

**明确不做的事**：**不**因为"真实模型可能输出不合规"就**放宽当前校验** ——
那会让确定性环境下已修好的缺陷重新潜伏。

**记录为待办**（非本轮缺口）：见 §5。

## 4. 对我自己行为的一条**结构性约束**（防复发）

鉴于 QA 指出的倒逼风险，我明确写入以下约束，供后续 TL 与 QA 共同监督：

| # | 约束 |
|---|---|
| 1 | **禁止**为让门禁变绿而**放宽校验、删除断言、调整阈值至刚好通过** |
| 2 | **禁止**把 READINESS 未达成**改写成**"不适用"或"已检查" |
| 3 | 结论**必须**写进文档（收口决议 / 判定包），**不得**仅靠门禁颜色表达 |
| 4 | 若某门禁**长期无法通过**，正确做法是**修正门禁语义或显式声明未达成**，<br>**不是**修改被测对象以迎合门禁 |
| 5 | 任何"判定标准变更"**必须**留下变更记录与理由 |

**第 4 条是本轮教训的直接产物**：
我先前把编译门禁写成"永不失败"，本质就是**修改门禁以迎合我想要的结论**。
