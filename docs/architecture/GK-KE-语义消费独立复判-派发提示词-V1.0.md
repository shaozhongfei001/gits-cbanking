# 派发提示词：§9.3 语义消费的**独立复判**

> **交给谁**：与 GK-KE 建设**无历史关联**的独立执行者（人或智能体）。
> **能由智能体完成吗**：**能。** 本任务不需要业务直觉或人工裁量，
> 只需要**按预注册判据逐条比对观测与结论** —— 这正是可验证、可复核的工作。
> **唯一硬约束**：**独立性**。执行者不得是建设过被判定对象的同一会话/同一人。

---

## 一、你的角色与边界

你是**独立判定执行者**。你**只判定**，不修改任何被判定对象。

**你不得做的事**（越界即判定作废）：
- 不得修改判据文档（`docs/architecture/GK-KE-语义级消费验证方案-*.md`）；
- 不得修改观测数据或 `report.json`；
- 不得修改被判定能力的实现；
- 不得以"我认为应该是"代替"观测显示"。

**你的结论将直接决定交付是否成立**，且**建设方无权推翻**。

---

## 二、背景（只读了解，不得据此推断结论）

本仓曾以 §9.3 的"七行消费表"声称：上游能力（事实对账）的输出**已被下游能力（KYC 缺口）消费**。
后续核查发现该声称**存疑**，遂建立判据 S1–S5 要求**以观测证据**判定，
而非以文档或代码存在性判定。

**你最需要警惕的一件事**：本领域已反复出现
**「文本说对、结论说错」**的形态 —— 例如下游在 `warnings` 里写了
"规则覆盖不足""覆盖状态待核实"，**但结论字段 `kycGaps` 是空的**。
故**任何基于关键词/文本的启发式都会误判**；必须看**结论字段本身**。

## 四、你要交付什么（逐项，缺一不可）

### 交付物 1：逐判据判定表

对 **S1–S5 每一条**给出：

| 列 | 要求 |
|---|---|
| `judgement` | **只能取 `PASS` / `FAIL` / `INCONCLUSIVE` 三者之一** |
| `basis` | **引用观测中的具体字段与值**（不是文件名、不是行号、不是"看起来"） |
| `counterExampleTried` | **你为推翻该结论尝试过的可执行反例**（若未尝试，写"未尝试"——这会被记为你未完成任务） |

**关于 `INCONCLUSIVE`**：
- 它**不等于通过**，也**不等于失败**；
- 当**证据不足以判定**时必须用它，**不得**用 `PASS` 或 `FAIL` 顶替；
- 用 `INCONCLUSIVE` 时**必须写明缺什么证据才能判定**。

### 交付物 2：`§9.3` 七行消费表逐行判定

对七行**逐行**给出：`达成 / 未达成 / 无法判定`，并**引用观测字段**。
**若某行的上游来源在映射合同中登记为"未映射"，该行必须判未达成或无法判定。**

### 交付物 3：反例清单

列出你构造的**每一个可执行反例**（命令 + 期望 + 实际）。
> **说明**：曾有一轮独立复核通过构造反例，发现了建设方设计中的**设计级缺陷**。
> **反例是本次判定最有价值的产物，不是附加项。**

### 交付物 4：你**未能**判定的部分与原因

如实列出。**"没查清"必须明说，不得用"通过"包装。**

## 五、判定纪律（违反任一条即判定作废）

1. **禁止用文本启发式**。结论必须来自**结论字段**，不是 warnings/描述/日志。
2. **禁止把"未执行"当成"没有"**。`NOT_RUN` / 空集合 / `NOT_PROBED`
   **不得**被读成"查了、没问题"。（判据里 `S2_EMPTY_MEANS_NONE` 与
   `S3_NOT_RUN_NOT_NONE` 就是为此设立的。）
3. **禁止把"上限"当"实测值"**。同理，`INCONCLUSIVE` 不得计入通过数。
4. **每条判定必须可复现**：写出你运行的命令。**只写结论不写命令的判定不予采信。**
5. **禁止推测**。你可以**读代码生成假设**，但**只有运行能确立结论**。
   > 本领域实测教训：连续两次"读代码推测出缺陷"，两次被运行结果证伪。
6. **不得修改任何被判定对象**（见 §一）。
