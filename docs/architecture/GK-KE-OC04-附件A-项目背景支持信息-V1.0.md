## A1. 项目是什么

**GK-KE**（知识工程）是银行的**对公客户经理"访前准备"智能体**项目的一个子交付。
目标：客户经理拜访企业客户前，系统自动装配该客户相关的**行内数据 + 行外数据 + 行业研判**，
生成一份「访前作战单」，把准备时间从**数小时压缩到数分钟**。

**关键角色**：
| 角色 | 职责 |
|---|---|
| Owner | 业务决策、条件裁定 |
| Tech Lead（我） | 合同与定义、编排、不写实现、不自签 |
| Feature Pilot | 实现 |
| Independent QA | 独立核验（**不得由 TL 代签**） |

**项目铁律**（贯穿全程，外部专家可据此判断我方是否越界）：
1. **合同先行**：改 `specs/` → 生成 → 再写实现
2. **不谎称已实现**：未实现的必须标 `CANDIDATE` / `DESIGN_ONLY`，不得升级状态
3. **不代签**：Owner 决议、QA 结论不得由 TL 代签
4. **SIM 性质**：本包为模拟，**不构成杭银正式口径**

## A2. 为什么会有 OC-04 这个条件

OC-04 是 Owner 在早期决议（OWNER-001）中提出的**4 个附条件之一**，主题为「**地图和能力**」。
含义：**访前准备任务的知识地图是否完整、引用的能力是否真实可用的**。

**当前触发复核的原因**：Owner 在人工验收台判定 OC-04 **「需调整」**，原话：

> 「客户方前准备，要查这三项资料（产品条款、日均存款、解读能力）还不够，
> 客户经理专业能力并不比客户强，还要准备产业调研、客户准入条件等信息」

**我方对该意见的理解**：缺口是「**知识广度**」而非「节点数量」——
不是我少画了两个节点，而是**节点背后指向的知识条目与能力太少**。

## A4. 本轮已完成的工作（路径 A）

Owner 指示「先 A 后 B」，A = 在 GK-KE 侧补成**可验收的定义**；B = 去 KERT 仓写实现。

### A4.1 知识广度（对标 7 类条目）
已补：7 类知识条目 + 2 项准入类规则知识 + 1 项流程知识；地图节点由 4 增至 19。

### A4.2 指标集（本次调研重点）
Owner 授权「做同业调研**自行决定**加哪些指标」。我方公开调研后确定 **14 项、三层**：

| 层 | 指标 | 数据源 |
|---|---|---|
| ① 经营真实性与活力（外部交叉验证） | 营收、用电量、纳税额/开票额、社保缴纳人数、进出口额/结售汇 | T-CORE-001 / T-EXT-001 |
| ② 行内合作与贡献 | 结算量、日均存款、代发薪、授信使用率、票据业务量、中间业务收入 | T-CORE-001 |
| ③ 风险与异常 | 逾期/欠息/展期、涉诉/被执行/股权变更、上下游集中度 | T-CORE-001 / T-EXT-001 |

**我方调研依据的公开来源**（请专家评估这些来源是否可靠、是否被误用）：
1. **上海农商银行「对公智能营销助手 · 访前透视镜」**（2026-05，公开报道）
   —— 访前报告覆盖五类：全景画像 / 财务健康度 / 合作现状 / 潜在需求 / **风险预警**；
   准备时间从约 1 小时缩短至数分钟。
   **限制**：公开报道**只给维度框架，未披露明细字段**。
2. **金税四期企业税务风险监控**（2026，多篇公开分析）
   —— 打通税务、银行、社保、海关、**外汇**、市场监管等 7 大部门数据。
   **启示**：支持加入纳税/开票、社保人数、进出口/结售汇作为交叉验证源。
3. **对公小微全生命周期动态风险管理**（九江银行公开案例，2025-11）
   —— 强调**动态管理**与客户"流动性"。
4. **贷后检查与资金监控实操**（2025-09）
   —— 关键风险指标（KRI）：不良率、逾期率、拨备等。
5. **神州信息「对公智能营销助手」**（厂商方案页）
   —— 目标为节省客户经理搜集资料时间，解决"行内政策与专家经验解读不足"。

**刻意不纳入**（附我方理由，请质疑）：
| 不纳入 | 我方理由 |
|---|---|
| 净利润、资产负债率等**财务报表指标** | 报表有滞后与粉饰风险；本包以行内交易数据 + 外部可验证数据为主 |
| 行业景气指数 | 属 KI-FRONT-002 八维研判负责，避免重复 |
| 客户经理主观评价 | 不可验证，违反「结论须有原文/数据支持」的合同要求 |

### A4.3 交叉验证规则（本次调研重点）
设计理念：**单指标看趋势不够，跨指标矛盾才是真信号**。

| 规则 | 条件 | 处置 |
|---|---|---|
| XC-1 营收-税务背离 | 营收↑ 但纳税/开票额↓或持平 | 标 TO_VERIFY + 生成话术 |
| XC-2 用工-代发背离 | 社保人数↑ 但代发薪↓ | 标 TO_VERIFY + 生成话术 |
| XC-3 用电-营收背离 | 用电量↓ 但营收↑ | 标 TO_VERIFY + 生成话术 |
| XC-4 额度-风险背离 | 授信使用率趋满 且 出现逾期/欠息 | **升级为风险预警** |

**约束**：交叉验证**只标注"待核实"+ 生成话术**，**不产生授信结论**
（这是项目已确认的合规边界：系统只给人建议，不做授信判断）。

## A5. 工程侧已有保障（供专家判断"是否只有形式"）

| 机制 | 说明 |
|---|---|
| 门禁 | **19 个**自动化门禁，全 PASS |
| **变异测试** | **13/13** 变异被捕获 —— 即"故意破坏断言逻辑，门禁必须转为失败"，用于证明断言**不是空转** |
| 诚实性断言 | 伪造"已实现"状态会被门禁拦下（含源码级证据要求） |

**此项的意义**：本程序曾**反复出现"假绿"**——6 个模块首报"门禁全绿"但断言实际为空转。
现已用变异测试系统性排除该问题。**故工程形式上的"通过"可信度较高，
本次外部调研的重点应放在"业务实质是否合理"**。

| # | 弱点 | 涉及调研项 |
|---|---|---|
| W-1 | ①层 4/5 项来自外部数据，**实际可得性与时延未验证** | 项 1 |

| W-3 | 交叉验证规则**无量化阈值与观察窗口**（只有方向 ↑/↓） | 项 2 |
| W-4 | 矛盾可能有**合法反向解释**（税收优惠、产品升级），误报风险未评估 | 项 2 |
| W-5 | XC-4 自动化"升级为风险预警"——**判断权是否应交人** | 项 2 |
| W-6 | 准入条件（KI-RULE-002）**只有抽象引用，无具体规则内容** | 项 3 |
| W-7 | 能力间数据流是**声明式关联**，未定义实际传递契约 | 项 3 |
| W-8 | `boundary` 是**文档级声明**，无运行时强制机制 | 项 3 |
| W-9 | 指标集可能**未考虑行业差异**（制造/贸易/服务应否分集） | 项 1 |
| W-10 | 为补 OC-04 而扩展的指标与能力，**可能超出原定试点范围** | 项 4 |

## A7. 术语表

| 术语 | 含义 |
|---|---|
| **KI** | Knowledge Item，知识条目（如 KI-FRONT-001 供应链图谱） |
| **TASK-FRONT-00x** | 访前准备的子任务编号 |
| **能力（Capability）** | 系统可调用的技能（Skill），如"八维研判能力" |
| **访前作战单** | 客户经理拜访前拿到的整合报告（一页 H5 + PDF） |
| **对账** | 核对行内数据与外部数据是否一致、有无矛盾 |
| **EXIT / OC** | Owner 设置的**附条件**（Owner Condition），逐项关闭 |
| **DESIGN_ONLY** | 仅有设计文档、无代码实现的诚实状态标注 |
| **TO_VERIFY** | 对账发现矛盾时的标注，意思是"需人工核实"，**不是结论** |
| **授信结论** | 是否批准贷款、给多少额度等——**本系统禁止产生** |
